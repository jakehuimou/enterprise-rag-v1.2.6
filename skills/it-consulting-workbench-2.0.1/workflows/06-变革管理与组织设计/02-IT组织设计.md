# IT组织设计 (IT Organization Design)

## 目标

设计匹配IT战略和数字化目标的高效IT组织, 包括组织结构、岗位定义、能力模型、人员规模、过渡计划。

---

## 前置条件
- IT战略方向已确定
- 当前IT组织已有评估(来自诊断阶段)
- 了解企业的组织文化和人才市场状况

## 输入物
- IT战略规划 (来自workflow 03-01)
- IT现状诊断报告-组织维度 (来自workflow 02-03)
- 当前IT组织架构图+人员清单
- 企业整体组织架构(了解IT在企业中的定位)

---

## 操作步骤

### 第一步: IT组织定位确定

#### 1.1 IT在企业中的三种角色

| 角色 | 定义 | IT的定位 | 典型组织形态 |
|------|------|---------|------------|
| **Utility** (公用事业) | IT=成本中心, 目标是"稳定+省钱" | CIO向CFO汇报 | 集中式, 运维为主 |
| **Partner** (业务伙伴) | IT=业务赋能者, 目标是"助力业务增长" | CIO向CEO汇报 | BU Partner + 共享平台 |
| **Driver** (增长驱动) | IT=核心竞争力, 目标是"用技术创造新业务" | CIO/CTO=核心决策层 | 产品化/平台化, 技术融入业务 |

**关键决策:** 客户的IT组织应该扮演什么角色? 这不仅决定组织设计, 也决定CIO的画像和薪资水平。

#### 1.2 IT组织演进方向

```
传统IT组织:                      现代IT组织:
                               
CIO                             CIO/CDO/CTO
├── 应用开发                    ├── 产品与平台 (Product & Platform)
├── 基础设施                    │   ├── 产品线A (业务对齐)
├── 运维                        │   ├── 产品线B
├── 安全                        │   └── 平台工程 (共享)
├── 数据(如果有)                ├── 企业架构与安全
└── PMO                         ├── 数据与AI
                                ├── 基础设施与云
                                └── 运营与支持
                                
"订单接收者"                    "价值创造伙伴"
```

### 第二步: 组织结构设计

#### 2.1 IT组织模式选择

| 模式 | 描述 | 优势 | 劣势 | 适用 |
|------|------|------|------|------|
| **集中式** | 所有IT资源统一管理 | 标准化+效率+成本控制 | 对业务响应慢 | 中小型企业 |
| **联邦式** | 总部IT + BU IT | 兼顾标准与灵活 | 重复+协调成本高 | 多元化大型企业集团 |
| **产品化** | IT按产品线/价值流组织 | 业务对齐好+速度快 | 可能重复建设 | 数字化原生企业 |
| **平台+产品** | 共享平台(基础设施/数据)+产品团队(面向业务) | 兼顾效率与灵活 | 需要强治理和协作 | 正在数字化转型的大中型企业 |

**推荐演进路径:**

```
大多数传统企业:
集中式 → 平台+产品 → (成熟后)可选择进一步产品化或保持平台+产品
```

#### 2.2 平台+产品模式详细设计

```
┌─────────────────────────────────────────────────┐
│                  CIO / CTO                       │
├─────────────────────────────────────────────────┤
│                                                   │
│  ┌──────────── 产品线 ────────────┐               │
│  │                                │               │
│  │ Product VP (业务对齐)           │               │
│  │  ├── Product Team: 客户域       │               │
│  │  │   └── PM + 开发 + UX + 数据  │               │
│  │  ├── Product Team: 交易域       │               │
│  │  ├── Product Team: 风控域       │               │
│  │  └── Product Team: 数据智能     │               │
│  │                                │               │
│  └────────────────────────────────┘               │
│                                                   │
│  ┌──────────── 平台层 ────────────┐               │
│  │                                │               │
│  │ Platform VP (共享能力)          │               │
│  │  ├── 云与基础设施平台            │               │
│  │  ├── 数据平台                   │               │
│  │  ├── 安全与合规平台              │               │
│  │  ├── DevOps/工具链平台           │               │
│  │  └── 企业架构                   │               │
│  │                                │               │
│  └────────────────────────────────┘               │
│                                                   │
│  ┌──────────── 卓越中心 ──────────┐               │
│  │  AI CoE | 敏捷CoE | 架构CoE    │               │
│  └────────────────────────────────┘               │
│                                                   │
└─────────────────────────────────────────────────┘

产品团队: "我们负责做什么+怎么做" (What + How for Business)
平台团队: "我们提供可复用的能力, 产品团队不用重复造轮子"
CoE: "我们提供最佳实践/工具/方法论, 确保大家不重复踩坑"
```

#### 2.3 关键角色定义

| 角色 | 汇报给 | 核心职责 | 需要的能力 |
|------|--------|---------|----------|
| **CIO** | CEO/CFO | IT战略+IT与业务对齐+重大投资决策 | 战略思维+业务理解+领导力 |
| **CTO** | CIO/CEO | 技术战略+架构+技术前瞻 | 深厚技术+创新+工程文化 |
| **CDO/CDAO** | CIO/CEO | 数据战略+数据治理+AI落地 | 数据+AI+业务理解 |
| **Product VP** | CIO | 产品线P&L(如适用)+产品战略 | 产品管理+业务+技术 |
| **Platform VP** | CIO | 平台能力建设+SLA+效率 | 架构+工程+DevOps |
| **CISO** | CIO/董事会 | 安全战略+风险+合规 | 安全+风险+业务沟通 |
| **Product Manager** | Product VP | 产品愿景+路线图+需求优先级 | 产品+用户研究+数据分析 |
| **Engineering Manager** | Product VP/Platform VP | 团队+交付+工程质量 | 技术+管理+敏捷 |
| **Site Reliability Engineer** | Platform VP | 可用性+性能+自动化运维 | 深度技术+系统思维+编程 |
| **Data Engineer** | 数据平台 | 数据管道+数据质量+数据平台 | 数据工程+分布式系统 |

### 第三步: 团队规模与能力规划

#### 3.1 人员规模基准

| IT人员占总员工比 | 行业 |
|-----------------|------|
| 2-4% | 制造业/传统零售 |
| 4-7% | 金融服务/保险 |
| 7-12% | 正在进行数字化的企业 |
| 20-50% | 科技/软件/SaaS企业 |

#### 3.2 人员结构比例

世界级IT组织的人员分布:

| 类别 | 占比 | 说明 |
|------|------|------|
| 产品/业务对齐角色 (PM/BA/产品设计师) | 20-25% | 确保技术做的是业务需要的 |
| 平台/工程角色 (工程师/架构师/SRE) | 45-55% | 真正的"造东西的人" |
| 运维/支持角色 | 10-15% | 随自动化逐步降低 |
| 安全/合规 | 5-8% | |
| 管理/PMO | 5-7% | |

**警示:** 如果运维/支持>25%, 说明自动化水平太低; 如果管理/PMO>10%, 说明管理层臃肿。

#### 3.3 技能缺口矩阵

| 关键技能 | 当前人数 | 需要人数 | 缺口 | 填补方式(招/培养/外包) |
|---------|---------|---------|------|---------------------|
| 云架构(AWS/Azure) | 2 | 8 | +6 | 招3 + 内部培养3 |
| AI/ML工程 | 0 | 5 | +5 | 招2(Lead) + 培养3 |
| 产品管理 | 1 | 6 | +5 | 招3(外部) + 转岗2(内部BA) |
| DevOps/SRE | 3 | 10 | +7 | 培养5 + 招2 |
| 数据工程 | 1 | 8 | +7 | 招4 + 培养3 |
| 遗留系统(COBOL...) | 3(快退休) | 2(过渡期) | -1 | 外部供应商 |

### 第四步: 人才策略

#### 4.1 建-买-租决策 (Build-Buy-Rent)

| 角色类型 | 策略 | 理由 |
|---------|------|------|
| 核心架构/技术决策 | **Build** (培养/招) | 核心能力不能外包 |
| 通用开发/测试 | **Rent** (外包) | 灵活增减, 成本可预测 |
| 稀缺高端人才(AI/安全) | **Buy** (高薪招) | 市场上抢人 |
| 遗留系统维护 | **Rent** (外包) | 过渡期策略 |
| 业务分析师 | **Build** (内部转岗) | 懂业务>懂技术 |
| 运维(非核心) | **Rent** (托管服务) | 自动化+外包 |

#### 4.2 关键留人策略

IT人员离职率通常15-25%, 高于企业平均。留人策略:

| 因素 | 为什么重要 | 建议 |
|------|----------|------|
| 技术成长 | IT人员最怕"技术被掏空" | 培训预算≥$3K/人/年, 每季度有学习日 |
| 做有意义的事 | 没人愿意一直修Bug/写报表 | 让工程师参与业务讨论, 理解"为什么做" |
| 现代工具 | 用古董工具=赶走最好的人 | 即使核心系统旧, 至少DevOps/工具链要现代化 |
| 薪酬 | 人才市场价格透明 | 至少50分位, 关键人才75分位+ |
| 自主权 | 工程师讨厌被微管理 | 给予技术决策自主权(在架构框架内) |
| 职业双通道 | 不是所有人都想/适合做管理 | 管理线+专家线(Principal→Distinguished→Fellow) |

### 第五步: 过渡计划

#### 5.1 从旧组织到新组织的过渡

```
Phase 1: 建立基础 (0-3月)
├── 确定新组织架构
├── 任命关键领导(CIO直接下属)
├── 沟通组织变化: 谁走向哪里
├── 识别"受影响的"人: 角色消失/变化的, 一对一沟通
└── 建立第一个产品团队(试点)

Phase 2: 核心过渡 (3-9月)
├── 产品团队扩展到2-3个
├── 平台团队从基础设施团队转型
├── 第一批培训/转岗完成
├── 敏捷/DevOps实践在试点团队跑通
└── 识别"变革阻碍者"并处理

Phase 3: 规模化 (9-18月)
├── 全组织按新架构运行
├── CoE运营常态化
├── 人才市场策略持续
└── 组织健康度回顾+调整
```

#### 5.2 组织变革中的人的维度

```
谁最受影响?
├── 中层IT管理者: 从"管人"→"带团队做产品" — 能力要求完全不同
├── 资深技术专家: 技术栈变了, 从"最懂的"→"要学习" — 身份危机
├── 运维人员: 从"手工操作"→"写代码自动化" — 核心技能变了
└── 业务联络人(BA): 从"传话的"→"产品经理" — 角色核心变了

每个人都需要:
- 清晰的沟通: "你的新角色是什么, 为什么, 怎么过渡"
- 培训/过渡期: 不是"从明天起你就是DevOps工程师了"
- 选择权: "你有这些选项: 学习新技能/转岗/拿遣散费离开(尊重)"
```

## 交付物
1. **IT组织定位声明**: 角色+汇报线+演进方向
2. **目标组织架构图**: 包含关键角色和人员编制
3. **岗位与职责描述**: 关键角色R&R
4. **人员规模与结构规划**: 人数+结构+技能缺口
5. **人才策略**: Build-Buy-Rent + 留人策略
6. **过渡计划**: 三阶段过渡+受影响人员安置

---

## 质量检查
- [ ] 组织设计支持IT战略(不是通用模板)
- [ ] 关键角色有明确职责和所需能力
- [ ] 技能缺口有具体填补计划(不是"需要招人")
- [ ] 过渡计划照顾了"受影响的人"(不只是组织架构图)
- [ ] 人员结构比例合理(运维<15%, 管理<10%)
- [ ] CIO的定位和汇报线明确

## 常见陷阱

| 陷阱 | 为什么错 | 正确做法 |
|------|---------|---------|
| 重画组织架构图=组织设计 | 画线很容易, 但改变人的行为/能力/文化才是真正的组织设计 | 架构图只是10%的工作, 90%是过渡+能力建设+文化 |
| 照搬互联网公司 | "我们也搞扁平化+产品+敏捷" — 但管理层没准备好放权, 文化不匹配 | 根据企业实际文化设计过渡方案, 有时候"改良"比"革命"更可行 |
| CIO位置太低 | 如果CIO向CFO汇报, IT永远被看作成本中心, 不可能做数字化驱动 | 争取CIO向CEO汇报(至少虚线) |
| 忽视中层管理者 | 中层是组织变革中最关键也最难的一层 — 失去权力最多, 需要改变最多 | 花最多时间在中层: 培训/教练/1on1/给新定位 |
| 大规模裁员代替转型 | "旧的不要了, 招新的" — 损失了业务知识, 破坏了士气, 新人也未必好用 | 优先给现有员工培训/转岗机会, 裁员是最后手段 |
