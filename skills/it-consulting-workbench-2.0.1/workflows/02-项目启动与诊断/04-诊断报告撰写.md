# 04 — 诊断报告撰写

## 目标
将五维诊断结果和利益相关者访谈发现，合成为一份逻辑严密、有洞见、能推动行动的诊断报告。诊断报告是后续战略设计的基础，也是客户判断你专业水平的第一个"真货"。

## 前置条件
- 五维诊断完成（技术/流程/组织/数据/财务）
- 利益相关者访谈完成
- 核心发现已经内部讨论并达成一致
- 行业对标数据已准备

## 输入物
- IT现状诊断记录（03-IT现状诊断.md的输出）
- 利益相关者访谈合成卡
- 行业基准数据

---

## 操作步骤

### Step 1: 发现→洞察→建议 三级提炼

在你开始写作之前，先把原始发现提炼为洞察：

```
原始发现 (What): 核心ERP系统基于15年前的技术架构，单次变更周期>3个月
      ↓  So What?
洞察 (Why it matters): 这意味着业务部门的新产品需求无法及时响应，
                      他们已经开始绕过IT自行采购SaaS解决方案
      ↓  Now What?
建议 (What to do): 启动ERP现代化项目，优先解决集成层和API化，
                  使业务部门至少可以自助获取数据

每个发现都必须通过"So What?"测试。如果你写完一句话，读者问"所以呢?"
而你没有准备好答案——删掉或改写。
```

### Step 2: 报告标准结构

```
封面页
  ├── 项目名称 / 客户公司 / 日期 / 密级

第一章: 执行摘要 (Executive Summary) — ≤2页
第二章: 诊断方法论概述 (1页)
第三章: 总体发现 (1-2页)
第四章: 分维度详细发现 (主要章节, 8-12页)
  ├── 技术维度
  ├── 流程维度
  ├── 组织维度
  ├── 数据维度
  └── 财务维度
第五章: IT成熟度综合评分 (1-2页)
第六章: 根因分析 (1-2页)
第七章: 快赢机会识别 (1-2页)
第八章: 建议与下一步 (1-2页)
附录: 详细数据/访谈清单/评分方法论
```

### Step 3: 逐章写作指南

**第一章: 执行摘要 — 诊断报告的灵魂**

标准结构:
```
第一段: 诊断范围和方法 (1-2句)
  "本次诊断覆盖了[公司]IT的五个核心维度——技术架构、流程效率、组织能力、
   数据就绪度、财务管理——通过[方法: 访谈X人/审查Y系统/分析Z数据/对标W标准]完成。"

第二段: 核心发现 (3-5个, 按重要性排序)
  "核心发现:
   1. [最重要的发现, 如: IT技术债务已累积到临界点——15个核心系统中有8个运行在EOL版本上]
   2. [...]
   3. [...]"

第三段: 总体成熟度评分
  "IT综合成熟度评分: 2.4/5 (行业平均3.1, 行业领先4.2)
   各维度: 技术2.0 / 流程2.5 / 组织2.8 / 数据2.0 / 财务3.0"

第四段: 关键建议的概要
  "建议优先推进三项行动:
   1. [快赢1] — 预计[时间], 投入[量级], 收益[量级]
   2. [快赢2]
   3. [战略级建议]"

第五段: 紧迫性声明
  "如果不采取行动，预计[时间]内[最严重的后果]。但好消息是，[核心优势/机会]为转型提供了良好起点。"
```

**第四章: 分维度发现 (每个维度的标准模板)**

```
4.X [维度名称] 维度

4.X.1 现状概览
  [2-3句说明该维度的整体情况]

4.X.2 核心发现
  发现 X.1: [标题: 发现+影响]
    ├── 现状: [具体描述, 含数据]
    ├── 影响: [对业务的具体影响, 量化]
    ├── 根因: [初步判断的原因]
    ├── 证据: [支持这个发现的证据来源: 访谈引用/数据分析/观察]
    └── 对标: [与行业平均水平/领先水平的差距]

  发现 X.2: [同上结构]
  ...

4.X.3 该维度优势
  [不要只写问题!每个维度至少1个做得好的地方]
  "尽管整体评分不高，[具体做得好的方面]值得肯定和保留。"

4.X.4 该维度主要风险
  [如果不改进，1-2年内最大的风险是什么]
```

**报告中有难度的措辞处理:**

```
不要写...                              改写为...
────────────────────────────────────────────────────────────
"IT团队能力明显不足"                    "IT团队在[具体技能领域]存在能力缺口，
                                       主要体现在[具体现象]。
                                       团队有[具体优势]，经过定向提升
                                       可以[预期效果]。"

"管理层不重视IT"                       "IT在组织中的战略定位有待提升——
                                       CIO汇报线为CFO(而非CEO)，
                                       IT预算占比低于行业平均40%。
                                       这导致[具体后果]。"

"系统架构一团糟"                       "技术架构经历了[X]年的有机增长和[M]次并购，
                                       目前存在[N]个技术栈并行、
                                       [Y]%的集成采用点对点方式。
                                       这是快速增长期的正常结果，
                                       但目前已达到需要系统性优化的拐点。"

"外包管理完全失控"                     "当前有[X]家IT供应商，合同管理方式不统一，
                                       其中[Y]%的合同缺乏SLA和退出条款。
                                       建议优先对Top [Z]家建立标准治理机制。"
```

### Step 4: 根因分析 — 用5-Why找到真正的原因

每个核心问题做5-Why分析:

```
例子:

问题: 新功能从需求到上线平均需要4个月

Why 1: 为什么?
→ 因为开发资源不足，经常在不同项目间切换

Why 2: 为什么资源不足?
→ 因为IT团队60%的时间花在维护老旧系统上

Why 3: 为什么维护时间这么高?
→ 因为15年历史的ERP系统没有文档，任何修改都需要反向工程+大量回归测试

Why 4: 为什么没有文档?
→ 因为过去10年没有人被要求写文档，"交付速度"一直被优先于"可维护性"

Why 5: 为什么速度优先于可维护性?
→ 因为IT的绩效考核只衡量"项目按时上线率"，不衡量"系统长期健康度"

根因: IT绩效体系激励了短期交付行为，导致了长期技术债务的系统性累积。
(如果只停留在Why 2"资源不足"，解决方案可能就是"加人"——这治标不治本)
```

### Step 5: 快赢机会识别

**快赢三要素: 高影响 + 低投入 + 高可见度**

```
快赢评分矩阵:

机会                业务影响  实施难度  时间     可见度  推荐优先级
                    (1-5)    (1-5↓)   (周)     (H/M/L)
──────────────────────────────────────────────────────────
清理僵尸云资源        4        1        2        M       ★★★ #1
建立IT服务目录        3        2        4        H       ★★★ #2
自动化3个高频报表     4        2        3        H       ★★★ #3
ERP核心升级          5        5        52       M       ★ (战略级, 非快赢)
组织架构重组          4        5        26       H       ★ (战略级, 非快赢)
```

### Step 6: 展示成熟度评分

```
IT成熟度雷达图 (文字描述):

              技术
              /\
             /  \
            /    \
           /  2.0 \
          /        \
   财务  / 3.0    2.5 \ 流程
        │            │
        │   2.4      │
        │   (总体)   │
        │            │
   数据  \ 2.0    2.8 /  组织
          \        /
           \      /
            \    /
             \  /
              \/

行业对比:
  客户评分:   2.0  2.5  2.8  2.0  3.0 = 2.4/5.0
  行业平均:   3.2  3.0  3.5  2.8  3.5 = 3.2/5.0
  行业领先:   4.5  4.2  4.5  4.0  4.5 = 4.3/5.0

最大差距: 技术(2.0 vs 4.5) 和 数据(2.0 vs 4.0) — 这两个维度应优先投资
```

## 交付物
1. **诊断报告**: 完整的8章诊断报告 + 附录
2. **成熟度评估**: 五维雷达图 + 行业对标
3. **根因分析**: 5-Why深入至系统性根因
4. **快赢机会清单**: Impact/Effort矩阵排序
5. **核心建议**: "如果只能做三件事"优先级

## 质量检查

- [ ] 执行摘要可独立阅读, 所有关键信息都在2页内
- [ ] 每个发现都通过了"So What?"测试
- [ ] 每个维度至少有1-2个数据支撑的发现
- [ ] 根因分析至少深挖到Why 3+
- [ ] 没有"能力不足""管理层不重视"等空洞判断，都转化成了具体可观测的现象
- [ ] 报告既指出了问题，也肯定了优势
- [ ] 快赢机会有明确的Impact/Effort评估
- [ ] 成熟度评分有对标数据,不是"感觉分"
- [ ] 读完整份报告，读者知道"最紧急的三件事是什么"

## 常见陷阱

| 陷阱 | 正确做法 |
|------|---------|
| 报告=问题列表, 没有优先级 | 必须有"如果只能做三件事"的排序。客户要的是方向，不是百科全书 |
| 用"行业最佳实践"压客户 | "XX公司做了XX" — 这不是好论点。指出"你们的情况适合用XX模式，因为..."才是 |
| 每个发现都指向同一批根因 | 如果所有问题的根因都是"管理层不重视IT"，你还没挖够深 |
| 过度诊断 (分析瘫痪) | 诊断是为了行动。一个方向性正确但立马能推的建议 > 10个还在验证中的完美分析 |
| 不敢写出真正的困难 | 诚实 > 讨好。如果问题严重，用建设性语言说真相比粉饰太平更受尊重 |
