# 01 — 项目章程与团队组建

## 目标
签约后一周内：完成项目章程、组建项目团队、开好启动会(Kickoff Meeting)、让双方团队对齐。

## 前置条件
- SOW已签署
- 客户已指定项目接口人(通常是IT PMO或CIO办公室主任)

## 输入物
- 签署的SOW（含项目范围/交付物/时间表/费用）
- Proposal（了解项目背景和初步假设）
- 客户提供的背景材料

---

## 操作步骤

### Step 1: 制定项目章程(Project Charter) — Day 1-3

项目章程是项目的"宪法"，所有人对它的理解必须一致。

**项目章程模板:**

```markdown
# 项目章程 — [项目名称]

## 1. 项目概述
### 1.1 项目背景
[为什么启动这个项目？— 2-3句]

### 1.2 项目目标 (SMART)
- 目标1: [具体] [可衡量] [可达成] [与战略相关] [有截止时间]
- 目标2: ...
- 目标3: ...

### 1.3 项目范围
在范围内 (In Scope):
  - [具体可交付物/活动1]
  - [具体可交付物/活动2]

不在范围内 (Out of Scope) — 同样重要！:
  - [明确排除的内容1]
  - [明确排除的内容2]

## 2. 项目组织
### 2.1 治理结构
┌─────────────────────────────────┐
│     指导委员会 (SteerCo)         │  ← 战略决策/预算/重大变更
│     客户Sponsor + 我方合伙人     │     月度会议
├─────────────────────────────────┤
│     项目核心团队 (Core Team)      │  ← 日常决策/专题推进
│     客户PM + 我方PM + 关键专家   │     周例会
├─────────────────────────────────┤
│     工作组 (Workstreams)         │  ← 执行层面
│     WS1 / WS2 / WS3             │     根据需要
└─────────────────────────────────┘

### 2.2 角色与职责 (RACI矩阵)
任务                  客户Sponsor  客户PM  我方PM  技术专家  业务专家
项目目标批准              A          R       C       I        C
关键交付物签字            A          C       R       I        I
日常决策(<5%范围变更)      I          C       A       R        R
重大变更(>5%范围/预算)     A          R       C       I        I

A=Accountable(最终负责) R=Responsible(执行)
C=Consulted(需咨询)     I=Informed(需告知)

### 2.3 团队名单
| 角色 | 姓名 | 组织 | 投入比例 | 联系方式 |
|------|------|------|---------|---------|
| 执行发起人 | | | | |
| 客户项目经理 | | | | |
| 我方项目经理 | | | | |
| 业务专家 | | | | |
| 技术专家 | | | | |

## 3. 项目计划
### 3.1 里程碑时间表
里程碑              计划日期    验收标准
Kickoff启动会         W1        [标准]
中期汇报              W6        [标准]
初版交付物评审         W10       [标准]
最终交付物评审         W14       [标准]
高管层最终汇报         W16       [标准]
项目收尾              W18       [标准]

### 3.2 关键依赖
- [我方依赖客户提供的X数据]
- [客户依赖第三方供应商Y的配合]

## 4. 沟通计划
沟通事项            受众        频率      渠道        负责人
项目周报            核心团队     每周五    邮件         我方PM
月度SteerCo汇报     指导委员会   每月     会议+PPT     我方PM
风险升级            指定人员     即时     电话/当面    双方PM

## 5. 风险管理
详见风险登记册(项目启动后一周内建立)
- 已识别的Top3风险:
  1. [风险描述] — 概率[高/中/低] 影响[高/中/低]
  2. ...
  3. ...

## 6. 签署
[客户Sponsor]          日期: ________
[我方合伙人]            日期: ________
[客户项目经理]          日期: ________
[我方项目经理]          日期: ________
```

### Step 2: 开好启动会(Kickoff Meeting) — Day 3-5

**会前准备清单:**
- [ ] 项目章程草案已完成并内部审阅
- [ ] 所有关键利益相关者已确认参会
- [ ] 会议室/线上链接已预订
- [ ] 演示材料已准备(通常15-20页)
- [ ] 已了解上次和客户沟通后的任何新情况

**启动会议程 (90分钟标准版):**

```
0-5min:   开场与Sponsor致辞（为什么这个项目重要）
5-15min:  团队介绍 (每个人Name/Role/Why I'm here)
15-25min: 项目章程宣讲 (目标/范围/计划/治理)
25-40min: 方法论与工作方式介绍 (会怎么做/为什么这么做/你们需要做什么)
40-55min: 风险与关注点讨论 (开放式讨论: "你担心什么?")
55-75min: 下一步详细安排 (前2-4周的具体工作计划)
75-85min: Q&A
85-90min: 总结 + "成功是什么样的"共识确认
```

**启动会上的关键行为:**

1. **Sponsor必须讲话**: 如果客户Sponsor没来或没讲话，这是个危险信号。想办法确保Sponsor至少开场2分钟，说"这个项目对公司很重要"——这句话值千金。

2. **建立心理安全感**: 在"风险与关注点讨论"环节主动示弱：
   > "每个项目都有不确定性。我想请每个人说一个你担心的事情——这比假装一切完美有用得多。我带头——我担心的是客户的某些关键数据可能分散在太多部门，收集会花比预期更长的时间。"

3. **让客户团队看到"对他们有什么好处"**: 每个工作流说明不仅讲要做什么，更要讲"做完后你的日常工作会有什么变化"。

### Step 3: 建立信息基础设施 — Day 1-5

```
必须创建的事项:
  □ 项目共享文件夹(SharePoint/Google Drive/飞书)
    └── 01-项目管理/ (章程/计划/状态报告)
    └── 02-客户输入/ (客户提供的材料)
    └── 03-分析工作/ (中间分析文件)
    └── 04-交付物/ (正式交付物)
    └── 05-会议与沟通/ (会议纪要/汇报材料)
    └── 06-参考材料/ (行业报告/外部数据)

  □ 沟通渠道
    □ 即时通讯群(企微/钉钉/Slack)
    □ 项目邮箱列表
    □ 升级路径 (什么情况升级到谁)

  □ 会议节奏日历
    □ 周例会: 每周X X:00-X:00 (60min)
    □ 月度SteerCo: 每月第X个周X (90min)
    □ 按需Workshop: 提前一周预约
```

## 交付物
1. **项目章程**: 包含6个部分的完整章程+RACI矩阵
2. **Kickoff会议纪要**: 含决策记录和行动项
3. **项目文件夹结构**: 标准化的信息基础设施
4. **风险登记册**: 初始风险评估

## 质量检查

- [ ] 项目章程所有6个部分已经填写完整
- [ ] RACI矩阵中每个关键任务都有A和R
- [ ] Out of Scope部分和In Scope一样清晰
- [ ] Kickoff会议纪要已24小时内发出
- [ ] 项目文件夹结构已建立
- [ ] 风险登记册已建立，Top5风险有缓解措施

## 常见陷阱

| 陷阱 | 正确做法 |
|------|---------|
| 章程写得漂亮但没人看 | 章程的核心价值在讨论过程——通过逐条确认让所有人对齐 |
| Kickoff变成你的独角戏 | 你的发言<50%时间，Sponsor+客户团队>50% |
| 风险登记册"一次性"建立再也不更新 | 每次周例会第一项议程就是更新风险 |
| 所有问题都通过正式渠道沟通 | 建立非正式沟通——和客户PM喝杯咖啡比10封邮件管用 |
