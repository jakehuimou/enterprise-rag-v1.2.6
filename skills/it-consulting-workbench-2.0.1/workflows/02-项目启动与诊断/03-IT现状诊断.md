# 03 — IT现状诊断

## 目标
对客户的IT现状进行系统化、结构化的全面诊断，覆盖技术/流程/组织/数据/财务五个维度，产出可评分、可对比、可追踪的现状基线。

## 前置条件
- 启动会已完成，团队已组建
- 已获得系统/文档访问权限
- 利益相关者访谈已安排（参见本阶段02-利益相关者访谈）

## 输入物
- 客户提供的技术文档（架构图/系统清单/运维数据等）
- 利益相关者访谈记录
- 行业对标数据（参见`references/基准数据与行业指标.md`）

---

## 操作步骤

### Step 1: 技术维度诊断 — 系统/架构/质量全景扫描

**1.1 应用系统组合盘点 (Application Portfolio Assessment)**

对每个主要系统，按以下矩阵评估：

```
系统名称   类型   业务关键度  技术健康度  业务适配度  建议动作
           SoR/    (1-5)      (1-5)       (1-5)       Keep/Modernize/
           SoD/SoI                                     Replace/Retire
──────────────────────────────────────────────────────────────
核心ERP    SoR     5          2           3           Modernize
CRM        SoD     4          4           3           Keep
旧报表系统  SoI     2          1           1           Retire
电商平台    SoD     5          3           4           Modernize
```

评分标准:
- 技术健康度: 1=严重技术债务, 5=现代云原生架构
- 业务适配度: 1=完全不能满足当前业务, 5=完美适配且有余量

**1.2 技术架构评估清单**

```
□ 架构风格 (单体/微服务/SOA/事件驱动/混合)
□ 编程语言与框架版本 (是否有EOL风险)
□ 数据库类型与版本 (RDBMS/NoSQL/Graph/TSDB)
□ 中间件/集成层 (ESB/API Gateway/消息队列/ETL)
□ 基础设施 (自建DC/托管/公有云/混合)
□ 容器化/编排水平 (裸机/VM/Container/K8s)
□ CI/CD成熟度 (手动→自动化→持续部署)
□ 可观测性 (日志/指标/追踪覆盖度和工具)
□ 灾备与高可用 (RPO/RTO/跨AZ/跨Region)
□ 技术栈一致性 (统一 vs 每个团队自己选)
```

**1.3 技术债务速评**

```
维度              评分(1-10)   证据
代码质量                        [Sonar评分/测试覆盖率/...]
架构复杂度                      [耦合度/循环依赖/...]
文档完整性                      [有无架构文档/API文档/...]
运维成熟度                      [自动化率/告警有效度/...]
安全基线的偏差                  [已知漏洞数量/补丁延迟/...]

技术债务总分: ___/50
行业参考: 顶尖<10分, 良好10-20分, 关注20-30分, 严重>30分
```

### Step 2: 流程维度诊断 — IT价值流的效率

**2.1 IT核心流程成熟度评估**

对每个核心流程，用CMM/CMMI 5级打分：

```
IT核心流程           成熟度(1-5)  关键痛点                 行业基准
需求管理                               需求变更率>30%           业界目标<15%
架构评审                               无正式评审流程
开发管理                               需求到上线平均___天      顶尖<7天
测试管理                               自动化测试覆盖率___%     >80%
变更管理                               变更失败率___%           <5%
发布管理                               发布频率___次/周         顶尖: on-demand
事件管理                               MTTR___小时             <1h
问题管理                               临时修复占比___%         <20%
容量管理                               资源利用率___%           60-80%
供应商管理                             供应商SLA达成率___%      >95%
```

**2.2 端到端流程效率 — 选3个核心价值流深挖**

选3个最重要的IT价值流(如"新功能从需求到上线""事故从发现到恢复""新供应商从选择到入場")，画时序泳道图：

```
价值流: 新功能从需求到上线
────────────────────────────────────────────────
步骤                耗时      等待时间    瓶颈?
需求提出与评审        2天      5天        ⚠️ 等待业务确认
技术方案设计          3天      2天
开发                  5天      1天
代码评审              1天      2天        ⚠️ 等待CR资源
测试                  3天      3天        ⚠️ 环境不稳定
发布审批              0.5天    4天        ⚠️ 审批链路过长
上线                  0.5天    0

总耗时: 32天 | 实际工作时间: 15天 | 等待浪费: 17天(53%)
行业顶尖: 总耗时<7天, 等待浪费<20%
```

### Step 3: 组织维度诊断 — IT团队和人

**3.1 组织结构分析**

```
□ IT向谁汇报? (CEO vs CFO vs COO — 决定了IT的战略地位)
□ IT团队总人数: ___人(占公司总人数___%)
□ IT人均支撑员工数: ___ (行业参考: 高科技1:20, 制造1:50, 金融1:30)
□ 自建 vs 外包比例: ___ : ___
□ 团队地理分布: (同城/跨城/跨国)
□ 组织结构类型: (集中式/联邦式/产品导向/平台+团队)
```

**3.2 IT人才技能矩阵**

```
角色/能力域        应有         现有         差距        重要性
                   人数         人数
EA/架构师           [x]          [y]          [z]         🔴关键
Product Manager     [x]          [y]          [z]         🟡重要
敏捷教练/Scrum Master [x]       [y]          [z]         🟢一般
DevOps/SRE          [x]          [y]          [z]         🔴关键
数据工程师          [x]          [y]          [z]         🔴关键
AI/ML工程师         [x]          [y]          [z]         🟡重要
安全工程师          [x]          [y]          [z]         🔴关键
```

**3.3 文化和能力诊断问题**
- "上次一个想法从提出到被实施用了多久?" → 衡量创新速度
- "最近一次系统故障是怎么处理的?" → 衡量工程文化和运维成熟度
- "业务团队怎么评价IT?" → 衡量IT的业务伙伴定位
- "你团队最好的工程师为什么要留在这里?" → 衡量人才吸引力

### Step 4: 数据维度诊断 — AI/分析的燃料

```
数据维度           现状评分(1-5)   关键发现
数据资产盘点                        □ 有完整的数据目录? (是/否)
数据质量标准                        □ 关键数据实体质量: 完整性__% 准确性__% 及时性__%
主数据管理                          □ 客户/产品/供应商主数据: 统一/分散/不存在
数据治理                            □ 数据Owner明确? 策略执行?
数据可访问性                        □ 分析师获取数据平均耗时: ___天
数据安全与隐私                      □ 分类分级? 脱敏机制?
BI/分析成熟度                       □ 报表/自助分析/AI驱动洞察/自动化决策 (在哪一层?)
AI就绪度                           □ 数据标注? 特征工程基础设施? 模型治理?
```

### Step 5: 财务维度诊断 — 钱花到哪里了

```
□ IT总支出: $___M/年 (占营收___%)
□ 人均IT支出: $___/员工/年 (行业基准: 金融$15-25K, 制造$5-10K)
□ Run/Grow/Transform: ___%/___%/___% (目标: 50/30/20)
□ 外包支出占比: ___%
□ 供应商集中度: Top3供应商占IT支出___%
□ 云支出: $___M/年, 预计浪费率___% (行业平均: 30-35%)
□ 近3年IT预算增长率: ___%/年
□ 重大IT项目的ROI追踪率: ___% (多少项目做了事后ROI评估)
```

## 质量检查

- [ ] 五个维度均已覆盖(技术/流程/组织/数据/财务)
- [ ] 每个维度的关键指标均已收集并评分
- [ ] 评分有证据支撑，不是"感觉"
- [ ] 与行业基准做了对比
- [ ] 识别了各维度的Top 3痛点
- [ ] 诊断发现已经和利益相关者初步验证（避免偏见）

## 常见陷阱

| 陷阱 | 正确做法 |
|------|---------|
| 只看系统不看人 | 技术诊断花2天，流程/组织诊断也要花至少各1天 |
| 评分偏主观（"我觉得技术债务是3分"） | 降维到具体指标：代码重复率/测试覆盖率/架构依赖数/已知漏洞数 |
| 诊断=批评大会 | 诊断是找"改进起点"，不是"证明你很差"。先讲做得好的地方 |
| 数据拿不到就不做了 | 始终有Plan B: 基于访谈估算 + 标注置信度 |
