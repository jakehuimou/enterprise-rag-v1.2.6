# 项目实施管理 (Project Implementation & PMO)

## 目标

管理IT项目的实施执行, 确保在范围/时间/预算/质量四约束下成功交付, 建立有效的项目治理和风险管理机制。

---

## 前置条件
- 项目章程已批准
- 项目计划已制定
- 团队已组建
- 供应商合同已签署(如涉及)

## 输入物
- 项目章程与计划
- 合同/SOW
- 预算与资源计划
- 风险管理计划

---

## 操作步骤

### 第一步: 项目治理建立

#### 1.1 项目治理架构

任何大型IT项目必须有三层治理:

```
┌─────────────────────────────────────────┐
│  战略层: 指导委员会 (Steering Committee)  │
│  成员: Sponsor(CIO+业务VP)+PM+供应商高管   │
│  频率: 月度(1-2小时)                      │
│  决策: 预算调整/范围变更/重大问题仲裁       │
├─────────────────────────────────────────┤
│  战术层: 项目核心团队 (Project Core Team)  │
│  成员: PM+Tech Lead+业务Lead+供应商PM      │
│  频率: 周度(1小时)                         │
│  决策: 进度管理/风险应对/资源协调           │
├─────────────────────────────────────────┤
│  执行层: 交付团队 (Delivery Teams)         │
│  成员: 开发/测试/BA/业务代表               │
│  频率: 每日站会(15分钟)                    │
│  决策: 日常技术决策/任务分配/障碍移除       │
└─────────────────────────────────────────┘
```

#### 1.2 RACI矩阵 (核心活动)

| 活动 | Sponsor | PM | Tech Lead | 业务Lead | 供应商 | 团队 |
|------|---------|----|-----------|---------|--------|------|
| 项目计划审批 | A | R | C | C | C | I |
| 需求签字确认 | A | R | C | R | I | C |
| 范围变更 | A | R | C | C | C | I |
| 技术方案审批 | I | A | R | I | C | C |
| 里程碑验收 | A | R | R | R | C | I |
| 预算审批 | A | R | I | I | I | I |
| 风险应对(项目级) | I | R | C | C | C | I |

*R=Responsible(执行), A=Accountable(最终负责), C=Consulted(需咨询), I=Informed(需知会)*

### 第二步: 项目计划与跟踪

#### 2.1 项目计划层次

```
里程碑计划 (Milestone Plan) — 给SteerCo/管理层看
├── M1: [日期] 需求确认完成
├── M2: [日期] 详细设计完成
├── M3: [日期] 开发完成
├── M4: [日期] 测试完成
├── M5: [日期] UAT完成
├── M6: [日期] 上线
└── M7: [日期] 上线后稳定期结束

阶段计划 (Phase Plan) — 给项目核心团队看
├── 每个阶段分解为具体的任务包
├── 每个任务包有负责人+截止日+依赖
└── 滚雪球式: 近2-4周详细, 后面的保持大纲级

Sprint/迭代计划 — 给执行团队看
├── 2周一个Sprint(或根据项目方法)
├── 每个Sprint有明确的Sprint Goal
└── Sprint Review + Retrospective
```

#### 2.2 进度跟踪

**每周必看的5个指标:**

| 指标 | 怎么算 | 绿灯 | 黄灯 | 红灯 |
|------|--------|------|------|------|
| SPI (进度绩效指数) | EV/PV | >0.95 | 0.85-0.95 | <0.85 |
| 完成率 | 已完成工作量/总工作量 | >按时间比例 | 略低 | 严重偏低 |
| 里程碑达成 | 按时完成数/应完成数 | 100% | 80%+ | <80% |
| 关键路径浮动时间 | 最晚开始-最早开始 | >2周 | 0-2周 | <0(延迟中) |
| 未解决阻塞项 | 阻塞>3天的任务数 | 0 | 1-2 | >2 |

#### 2.3 状态报告

**周状态报告一页纸:**
```
项目: [名称] | 报告期: [日期] | PM: [姓名]

整体状态: 🟢On Track / 🟡At Risk / 🔴Off Track

本周完成 (Top 3-5):
✅ [完成项1]
✅ [完成项2]

下周计划 (Top 3-5):
➤ [计划项1]
➤ [计划项2]

关键风险/问题 (Top 3):
⚠️ [风险/问题] — [影响] — [应对] — [负责人] — [预计解决日期]

需要帮助 (Escalation):
🆘 [需要谁做什么决定/行动] — [截止日期]

关键指标:
  进度: [X]% 完成 (计划[X]%)
  预算: 花费$[X]M / 总预算$[Y]M ([X]%)
  资源: [X]/[Y]人
  关键里程碑: M1✅ M2✅ M3➤(on track) M4⚠️(at risk)
```

### 第三步: 风险与问题管理

#### 3.1 风险vs问题

| | 风险 (Risk) | 问题 (Issue) |
|---|---|---|
| 定义 | 可能发生, 但现在还没发生 | 已经发生了 |
| 管理动作 | 预防+缓解 | 解决+升级 |
| 管理工具 | 风险登记册 | 问题日志 |
| 频率 | 双周-月审查 | 每日跟踪 |

#### 3.2 风险登记册

| ID | 风险描述 | 概率 | 影响 | 等级 | 应对策略 | 负责人 | 审查日期 | 状态 |
|----|---------|------|------|------|---------|--------|---------|------|
| R1 | 关键技术人员离职 | M | H | 🔴 | 建立备份+文档强制+保留奖金 | PM | 6/15 | 监控中 |
| R2 | 供应商交付延迟 | M | H | 🔴 | 合同罚则+每周交付审查+备选供应商 | 采购 | 6/15 | 监控中 |
| R3 | 数据迁移质量问题 | H | M | 🟡 | 数据质量检查自动化+提前迁移+回退方案 | Tech Lead | 7/1 | 监控中 |
| R4 | 业务方UAT参与不足 | M | M | 🟡 | 提前锁定业务方时间+UAT纳入其KPI | 业务Lead | 8/1 | 监控中 |

**风险应对策略:**
- **Avoid** (规避): 改方案, 让风险不发生 (如不用那个技术)
- **Mitigate** (缓解): 降低概率或影响 (如增加备份)
- **Transfer** (转移): 转嫁他人 (如买保险/外包/合同罚则)
- **Accept** (接受): 知道有风险, 但决定接受 (需记录+管理层认可)

#### 3.3 问题升级路径

```
发现问题 → 
├── 项目团队内能解决? → 解决+记录
├── 需要跨团队协调? → PM协调, 3天内无解升级到核心团队
├── 需要预算/范围/进度调整? → 核心团队讨论 → SteerCo决策
└── 项目级危机(重大延迟/超支/安全事件) → 24小时内升级到Sponsor
```

### 第四步: 质量管理

#### 4.1 质量保证(QA) vs 质量控制(QC)

| | Quality Assurance (QA) | Quality Control (QC) |
|---|---|---|
| 关注点 | 过程 | 产品 |
| 问题 | "我们在按正确的方式做吗?" | "我们做出来的东西对吗?" |
| 活动 | 流程审计/最佳实践/标准 | 测试/评审/检查 |
| 时机 | 持续 | 在关键节点 |

#### 4.2 质量门 (Quality Gates)

在以下节点设置质量检查:

```
Gate 1: 需求评审 (Requirements Review)
□ 需求是否完整、一致、可测试?
□ 非功能需求(性能/安全/可用性)是否明确?
□ 利益相关者是否签字确认?

Gate 2: 设计评审 (Design Review)
□ 设计是否满足需求?
□ 是否遵循架构标准?
□ 技术债务是否有明确记录和偿还计划?

Gate 3: 代码/开发完成
□ 代码评审率>90%?
□ 单元测试覆盖率>70%?
□ 安全扫描(SAST)无高危漏洞?

Gate 4: 测试完成
□ 所有测试用例执行完成?
□ 严重Bug=0, 高Bug<5?
□ 性能测试通过(满足NFR)?

Gate 5: UAT完成
□ 业务方签字确认?
□ 培训完成(目标群体>80%)?
□ 上线Checklist全部打勾?

Gate 6: 上线
□ 部署步骤文档化?
□ 回滚方案已验证?
□ 监控/告警已配置?
□ 支持团队就位?

Gate 7: 上线后稳定期
□ 连续7天无P1/P2事故?
□ 关键指标(KPI)达到预期?
□ 知识转移完成?
```

### 第五步: 范围与变更管理

#### 5.1 变更请求(CR)流程

```
任何人提出变更请求
  ↓
PM记录在变更日志
  ↓
PM+Tech Lead+业务Lead做初步影响评估(24-48小时)
  ↓
     影响评估: 对进度(+/-X天) + 成本(+/-$X) + 质量/风险
  ↓
├── 影响小(进度影响<1周+成本<$X) → PM可批
├── 影响中 → 核心团队评审+Sponsor知会
└── 影响大(进度影响>2周或成本>$X) → SteerCo审批
  ↓
批准? → 更新计划+预算+范围文档 + 通知所有受影响方
拒绝? → 记录理由+告知提出人
```

#### 5.2 范围蔓延(Scope Creep)预防

范围蔓延 = 项目做着做着, 范围一点点悄悄扩大, 但预算和时间没增加

| 预防措施 | 说明 |
|---------|------|
| 明确"不做"清单 | 项目范围也要说清楚"不包含什么" |
| 每个CR有成本 | 不是"顺便做一下", 是"这需要额外$X+Y天" |
| 月度范围审查 | 与SteerCo审查: "我们还在做我们承诺要做的吗" |
| 学会拒绝 | PM最重要的一句话: "这是个好主意, 我们可以放在Phase 2" |

### 第六步: 供应商管理 (日常)

#### 6.1 供应商绩效跟踪

| 维度 | 衡量方式 | 绿灯 | 红灯 |
|------|---------|------|------|
| 交付质量 | 缺陷密度/返工率 | 在约定标准内 | 超出标准 |
| 交付及时性 | 按计划交付的任务% | >90% | <70% |
| 响应速度 | 问题响应/解决时间 | 在SLA内 | 频繁超SLA |
| 团队稳定性 | 关键人员变更次数 | 无变更 | 频繁变更 |
| 沟通协作 | 主观评价 | 满意 | 不满意 |

#### 6.2 供应商周例会

```
议程(30分钟):
1. 上周完成什么? (供应商) — 10min
2. 下周计划做什么? (供应商) — 5min
3. 有什么阻碍/需要客户做什么? (供应商) — 5min
4. 质量/性能问题讨论 — 5min
5. 其他/行动项回顾 — 5min

输出: 会议纪要(24小时内) + 更新行动项清单
```

## 交付物
1. **项目治理架构**: SteerCo+核心团队+团队结构

3. **状态报告模板**: 周报+月报(SteerCo)

5. **质量门检查清单**: 每个Gate的通过标准
6. **变更请求日志**: 所有CR的记录和决策

## 质量检查
- [ ] 三层治理架构明确, SteerCo已开过第一次会
- [ ] 项目计划不是"一次写完再也不看" — 定期更新
- [ ] 风险登记册是活的(不是最初写了就再也没打开过)
- [ ] 质量门有明确的通过/不通过标准
- [ ] 变更管理流程在团队中周知且被执行
- [ ] 供应商绩效有数据(不是"感觉还行")

## 常见陷阱

| 陷阱 | 为什么错 | 正确做法 |
|------|---------|---------|
| PM做传话筒 | "业务说明天要, 技术说做不完, PM把两边话传一遍" | PM是问题的解决者和决策的推动者, 不是信使 |
| 计划精度妄想 | 一开始就做18个月的详细计划, 第2个月就全变了 | 滚动式规划: 近2-4周详细, 长期保持大纲级 |
| 风险登记册成摆设 | 写了但从来不在会议上审视, 直到风险变成了问题 | 每次核心团队会议花15分钟审视风险 |
| 所有问题自己扛 | PM不升级问题, 最后问题爆炸了才让Sponsor知道 | "坏消息早说" — 问题越早升级, 解决空间越大 |
| 牺牲质量赶进度 | "先上线再说, Bug后面修" → 后面=永远没时间修 | Bug债=技术债, 每个Sprint给Bug修复分配20-30%的时间 |
| 忽视团队健康 | 连续加班3个月 → 离职率飙升, 知识流失, 质量下滑 | 可持续节奏: 加班是例外不是常态; 庆祝小胜利; 关心团队 |
