# 项目验收与收尾 (Project Acceptance & Closure)

## 目标

系统化完成项目验收, 确保所有交付物达到验收标准, 正式移交, 关闭合同, 完成项目收尾和经验总结。

---

## 前置条件
- 所有项目交付物已完成(或剩余工作已转化为运维阶段的改进项)
- UAT已完成并签字
- 系统已上线并度过稳定期(通常30天)

## 输入物
- 合同/SOW中的验收标准
- 测试报告/UAT签字
- 交付物清单
- 未解决的问题清单(Known Issues)
- 合同条款(保固/Warranty/支持期限)

---

## 操作步骤

### 第一步: 验收准备

#### 1.1 验收标准审查

对照合同/SOW逐条审查:

| 验收项 | 标准 | 证据 | 状态 |
|--------|------|------|------|
| 功能需求(101条) | 全部通过UAT | UAT签字表 | ✅ 98通过, 3条作为Known Issues接受 |
| 性能需求 | P99<200ms | 性能测试报告 | ✅ |
| 可用性 | 99.9% (上线后30天) | 监控数据 | ✅ 99.95% |
| 安全合规 | 渗透测试无高危漏洞 | 渗透测试报告 | ✅ |
| 文档 | 运维手册+用户手册 | 文档仓库链接 | ✅ |
| 培训 | >90%培训完成率 | LMS报告 | ✅ 94% |
| 知识转移 | 内部团队可独立运维 | 知识转移确认签字 | ✅ |

#### 1.2 Known Issues管理

不是所有问题都需要在验收前解决。区分:

| 类别 | 定义 | 处理方式 |
|------|------|---------|
| **Blocker** | 验收不能过的(核心功能不可用/数据丢失) | 必须在验收前修复 |
| **Critical** | 严重影响使用但有Workaround | 可以验收, 但合同里约定修复时间(如30天) |
| **Minor** | 影响体验但不影响核心功能 | 记录为Known Issues, 转为运维阶段改善 |
| **Enhancement** | 不是Bug, 是新增需求 | 进入Backlog, Phase 2再做 |

**Known Issues登记:**
| ID | 描述 | 影响 | 级别 | 修复承诺时间 | 负责人 |
|----|------|------|------|-----------|--------|
| KI-001 | 导出超过10万行时报错 | 财务部月度导出受影响, 可分批导出 | Critical | 30天(Warranty) | 供应商-张工 |
| KI-002 | 界面在IE浏览器显示异常 | 仅2人使用IE | Minor | Phase 2 | — |

---

### 第二步: 正式验收

#### 2.1 验收会议议程

**参与者**: Sponsor(CIO+业务VP) + PM + Tech Lead + 供应商代表 + 采购

```
1. 项目回顾 (10min)
   - 项目目标 vs 实际达成
   - 关键里程碑: 按时/延迟? 说明原因

2. 交付物验收 (15min)
   - 按验收标准逐条确认
   - 未达标项的说明(为什么/怎么处理)
   - Known Issues清单确认

3. 关键指标签署 (10min)
   - 项目预算: 预算 vs 实际
   - 项目时间: 计划 vs 实际
   - 质量指标: 缺陷密度/可用性/性能

4. 移交确认 (10min)
   - 运维团队确认有能力接管
   - 文档/代码/配置/密钥 移交完毕

5. 验收决议 (5min)
   - 验收通过? 有条件通过?
   - 签署验收证书

6. 后续安排 (5min)
   - Warranty期限与范围
   - 运维支持过渡
   - Lessons Learned安排
```

#### 2.2 验收证书

```
项目验收证书

项目名称: [_________]
合同号: [_________]

兹证明:
上述项目已于 [YYYY-MM-DD] 完成所有合同约定的交付物。
验收基于以下文件:
  - 合同/SOW 编号 [_________]
  - UAT签字文件 日期 [_________]
  - 验收标准检查清单 日期 [_________]

验收决定:
□ 验收通过 — 所有交付物满足验收标准
□ 有条件通过 — 以下项目需在 [X] 天内修复:
    1. [_________]
    2. [_________]
□ 不通过 — 原因: [_________]

Warranty期: [YYYY-MM-DD] 至 [YYYY-MM-DD] (通常上线后30-90天)

签字:
客户方: __________________  日期: _________
(Sponsor/CIO)

供应商方: ________________  日期: _________
(授权代表)
```

### 第三步: 项目移交

#### 3.1 移交给运维团队

| 移交物 | 内容 | 状态 | 接收人 |
|--------|------|------|--------|
| 系统文档 | 架构图/部署图/数据字典/接口文档 | ✅ | 运维-李工 |
| 运维手册 | 日常运维SOP/故障处理/备份恢复/监控告警 | ✅ | 运维-李工 |
| 代码与配置 | 代码仓库/配置管理/CI/CD Pipeline | ✅ | DevOps-王工 |
| 账号与权限 | 所有系统账号清单+权限+密钥/证书 | ✅ | 安全-赵工 |
| 用户手册/培训材料 | 各角色使用手册+培训视频 | ✅ | 培训-陈主管 |
| 供应商联系信息 | 支持热线/升级联系人/合同信息 | ✅ | 采购-周经理 |
| 第三方依赖 | 第三方服务/API Key/许可证到期日 | ✅ | 运维-李工 |

#### 3.2 运维团队能力确认

```
□ 运维团队已参与至少2周的Shadowing(跟随项目团队)
□ 运维团队已独立处理过至少3个常见运维场景
□ 运维团队已参与1次故障演练
□ 运维团队有7×24值班安排
□ Escalation路径明确: 谁→谁→谁
□ On-Call手册已就绪(半夜3点被叫醒时知道怎么办)
```

---

### 第四步: 合同关闭

#### 4.1 财务结算

| 检查项 | 确认 |
|--------|------|
| 所有发票已收到并核对 | □ |
| 所有已完成工作的款项已支付(除保留金) | □ |
| 保留金(如合同有)是否到了释放条件? | □ |
| 是否有未结清的CR(变更请求)费用? | □ |
| 供应商保证金/押金是否需退还? | □ |
| 软件许可证/订阅是否已转至客户名下? | □ |
| 最终付款申请已提交? | □ |

#### 4.2 合同终止或转换

如果项目交付后继续有运维服务:
- 签署新的运维服务协议(或对原合同的Amendment)
- 明确Warranty期和付费运维期的边界

如果项目交付后完全结束:
- 正式的合同关闭函
- 供应商账号/权限回收
- 保留金释放(或扣除, 如果Warranty期内还有未解决问题)

---

### 第五步: 经验教训 (Lessons Learned)

#### 5.1 Lessons Learned Workshop

**参与者:** 项目团队+关键利益相关者+供应商代表
**时长:** 半天(3-4小时)
**氛围:** 不追责, 不批评, 聚焦于"下次怎么做得更好"

**议程:**
```
Part 1: What Went Well (60min)
"我们应该继续做什么?"
  - 每个人写Post-it → 归类 → 讨论
  - 识别可复用的最佳实践

Part 2: What Could Be Better (90min)
"什么可以做得更好? 下次怎么做?"
  - 不是"谁做错了", 是"什么制度/流程/工具让这个错误容易发生"
  - 每个问题必须有一个"如果下次...我们会..."

Part 3: Action Items (30min)
"具体要做什么来落实这些改进?"
  - 每个行动项有负责人+期限
```

#### 5.2 Lessons Learned报告

| 分类 | 发现 | 影响 | 建议(下次怎么做) | 负责人 | 期限 |
|------|------|------|---------------|--------|------|
| 需求管理 | 需求变更多, 但变更流程启动太晚 | 返工+进度延迟 | 从Day 1建立正式的CR流程+月度审查 | PMO | 纳入PMO标准流程 |
| 供应商 | 供应商关键人员被调走 | 知识断层+质量下降 | 合同中锁定关键人员, 后备人员需我方面试 | 采购 | 更新合同模板 |
| 测试 | UAT业务方参与不足 | Bug在上线后被发现 | 将UAT参与纳入业务方的KPI | 业务Sponsor | 下个项目启动时 |
| 沟通 | 中层管理者直到上线前2周才被通知 | 抵制+传播负面 | 中层管理者在项目启动时就纳入沟通对象 | 变革Lead | 纳入变革管理计划 |

---

### 第六步: 项目收尾庆祝

容易被忽略但非常重要的一步:

```
□ 给项目团队发自内心的感谢信(Sponsor/CIO亲自发)
□ 项目庆功会(哪怕只是午餐+简单致辞)
□ 每个人收到一份"你在项目中的贡献"的认可
□ 外部供应商团队也收到感谢
□ 关键贡献者获得邮件表扬(CC其上级)
□ 如果预算允许, 小小的项目纪念品
```

**为什么重要:**
- 项目结束后团队成员就要各奔东西, 这是最后一次凝聚
- 庆祝成功=给下一个项目建立正向预期
- 让大家愿意再次加入你的项目团队

## 交付物
1. **验收标准检查清单** (逐条通过/未通过/说明)
2. **Known Issues清单**
3. **验收证书** (双方签字)
4. **移交签收单** (运维团队签字)
5. **合同关闭文件**
6. **Lessons Learned报告**
7. **项目收尾庆祝** (是的, 这也是一个交付物)

---

## 质量检查
- [ ] 所有验收标准的"通过/未通过"有客观证据支撑
- [ ] Known Issues有明确的修复责任和时间承诺
- [ ] 运维团队已签字确认有能力接管
- [ ] 所有账号/密钥/证书/许可证已正式移交
- [ ] 所有财务事项已结清
- [ ] Lessons Learned是具体的行动项, 不是泛泛的"下次要加强沟通"
- [ ] Sponsor已签署验收证书

## 常见陷阱

| 陷阱 | 为什么错 | 正确做法 |
|------|---------|---------|
| "先验收了再说, 小问题后面再修" | 供应商拿到了验收证书和尾款, "小问题"就没人管了 | 小问题=Bug修复承诺在Warranty期内完成, 保留金扣留直到确认修复 |
| Known Issues没记录 | 验收时口头答应"这个后面修", 3个月后供应商不认 | 每个未解决问题的记录要正式, 签字确认 |
| 运维团队直到上线才介入 | "这是项目的事" → 项目结束, 运维接不住 | 运维团队在项目中期就参与, 最后一个月Shadowing+演练 |
| 不开Lessons Learned | 同样的错误在下个项目里重演(而且更严重) | Lessons Learned是项目的最后一个里程碑, 不做=项目没完 |
| 不庆祝 | 团队筋疲力尽, 项目结束=终于解脱, 没人想再干一次 | 庆祝不只是吃饭, 是认可和感谢, 是下次愿意再一起干的理由 |
