# 数据战略与治理 (Data Strategy & Governance)

## 目标

将数据定位为企业战略资产, 设计数据全生命周期管理体系, 制定从数据现状到数据驱动型组织的路线图。

---

## 前置条件
- IT现状诊断报告已包含数据维度评估
- 业务战略/IT战略方向已明确
- 了解客户所在行业的数据合规要求

## 输入物
- IT现状诊断报告 (数据架构/数据质量/数据治理现状)
- IT战略规划初稿
- 行业合规要求 (如GDPR/个人信息保护法/行业数据管理办法)
- 现有数据资产清单(如有)

---

## 操作步骤

### 第一步: 数据战略核心问题定义

**产出**: 数据战略问题陈述 (Data Strategy Problem Statement)

回答三个根本问题:
1. **数据今天在阻碍什么?** (如: "财务关账要7天因为数据要手工对账")
2. **数据明天能驱动什么?** (如: "如果能实时看到客户行为, 营销ROI可提升30%")
3. **如果不改变数据现状, 3-5年后会怎样?** (如: "数据孤岛每个部门建一套, 5年后整合成本是今天的10倍")

**填写模板:**
```
当前数据痛点TOP 5:
1. [痛点] → [影响: 多少钱/多少人/多少时间]
2. ...
3. ...

数据战略目标 (12-18个月):
- 数据治理: [如: 建立企业级数据治理委员会+数据Owner制度]
- 数据平台: [如: 建成统一数据平台, 核心业务域数据100%接入]
- 数据应用: [如: 上线3个数据驱动型业务用例]
- 数据文化: [如: 中层以上管理者100%完成数据素养培训]
```

### 第二步: 数据成熟度评估

#### 2.1 六维度数据能力评估

| 维度 | L1(初始) | L2(可重复) | L3(已定义) | L4(已管理) | L5(优化) |
|------|---------|-----------|-----------|-----------|---------|
| **数据战略** | 无正式战略 | 部门级数据策略 | 企业级数据战略 | 数据驱动业务决策 | 数据即产品/货币化 |
| **数据治理** | 无治理 | 部分数据标准 | 正式治理框架 | 自动化治理 | 生态级治理 |
| **数据架构** | 文件共享/手工 | 数据库/数据仓库 | Data Lake/Warehouse | Lakehouse/Data Mesh | 智能数据平台 |
| **数据质量** | 不知道好不好 | 被动修复 | 主动监控 | 源头预防 | AI驱动的质量自动修复 |
| **数据分析** | 报表(事后) | 描述性分析 | 诊断性+预测性 | 处方性+AI | 认知型(AI自主洞察) |
| **数据文化** | 数据=IT的事 | 部分业务用数据 | 数据素养培训 | 数据驱动决策常态化 | 数据=企业文化DNA |

**当前得分雷达图**: 标注每个维度的当前等级, 与行业基准对比。

#### 2.2 行业数据成熟度参考

| 行业 | 平均成熟度 | 领先成熟度 | 关键差距维度 |
|------|----------|----------|------------|
| 金融服务 | L3 | L4 | 数据治理强, 数据文化弱 |
| 制造业 | L2 | L3 | 数据架构差(OT/IT割裂) |
| 零售 | L2.5 | L4 | 数据分析强(营销), 数据治理弱 |
| 医疗 | L2 | L3 | 数据质量好, 数据共享差(隐私) |
| 政府 | L1.5 | L3 | 数据架构差, 共享意愿低 |

### 第三步: 数据治理框架设计

#### 3.1 数据治理组织结构

```
董事会/CEO
    │
    ├── 数据治理委员会 (Data Governance Council)
    │   成员: CDO(主席)+业务线VP+CIO+法务+合规
    │   频率: 月度
    │   职责: 战略方向, 政策审批, 重大数据问题仲裁
    │
    ├── CDO / Chief Data Officer
    │   职责: 数据战略执行, 数据资产管理, 数据价值实现
    │
    ├── 数据Owner (每个主题域一个, 由业务VP担任)
    │   数据主题域: 客户 / 产品 / 供应商 / 财务 / 员工 / ...
    │   职责: 本域数据"谁可以看/什么算好数据/冲突仲裁"
    │
    ├── 数据管家 (Data Steward, 可兼职)
    │   每个数据Owner下1-3人
    │   职责: 日常数据质量, 元数据维护, 数据问题一线处理
    │
    └── 数据架构/数据工程团队
        职责: 数据平台建设运维, 数据标准技术实现
```

#### 3.2 数据治理核心流程

**流程1: 数据标准制定**
```
业务提出 → 数据管家起草 → 数据Owner审核 → 数据治理委员会批准 → 发布→ 平台实施
```

**流程2: 数据质量事件处理**
```
发现问题 → 数据管家确认 → 级别判定(L1/L2/L3) → 
L1: 24小时内修复, 数据管家处理
L2: 72小时内修复, 数据Owner+IT协同
L3: 一周内, 上报数据治理委员会, 根因分析+预防措施
```

**流程3: 数据访问审批**
```
申请 → 数据Owner审批 → 最小权限授权 → 定期审计 → 超期自动回收
```

#### 3.3 数据标准定义

| 标准类别 | 示例 |
|---------|------|
| 命名规范 | 表名: `[域]_[实体]_[类型]`, 如`cust_profile_t` |
| 编码规则 | 客户ID: `CUST-{地区}-{8位流水}` |
| 数据字典 | 每个字段: 业务含义+数据类型+取值范围+来源系统 |
| 参考数据 | 国家码/币种/行业分类/... 统一取值 |
| 质量规则 | 必填/唯一性/取值范围/格式/关联校验 |

### 第四步: 数据架构设计

#### 4.1 数据平台选择决策

```
是否需要实时数据?
  ├── 是(延迟<1分钟) → 事件驱动架构(Kafka + Flink + 实时数仓)
  │   └── 选型: Streaming + Lakehouse (如Databricks/ClickHouse)
  │
  └── 否(批处理可接受) → Data Warehouse / Data Lake
      ├── 数据量<10TB + 简单BI → Data Warehouse (Snowflake/Redshift)
      ├── 数据量>10TB + 多源异构 → Data Lakehouse (Databricks/Iceberg)
      └── 多个BU有独立数据团队 → Data Mesh (联邦治理+数据产品)
```

#### 4.2 数据平台技术栈参考

```
数据摄入层:
├── 批处理: Airbyte / Fivetran / DataX
├── 实时流: Kafka + Flink / Spark Streaming
└── CDC(增量): Debezium / DMS

数据存储层:
├── 数据湖: S3/OSS + Iceberg/Hudi
├── 数仓: Snowflake / Databricks / Doris
├── 特征存储: Feast / Tecton
└── 图数据库: Neo4j / JanusGraph

数据加工层:
├── ETL/ELT: dbt + Airflow / Dagster
├── 数据质量: Great Expectations / Deequ
└── 数据血缘: DataHub / Marquez / OpenLineage

数据服务层:
├── BI: Tableau / Power BI / Metabase
├── 自助分析: Superset / 网易有数
├── 数据API: GraphQL + REST
└── 语义层: Cube / Looker
```

#### 4.3 数据架构演进的三个范式

| 范式 | 适用条件 | 优势 | 劣势 |
|------|---------|------|------|
| **集中式Data Warehouse/Lake** | 中小规模, BU自主性需求低 | 管控好, 一致性高 | 成为瓶颈, 难以扩展 |
| **Data Lakehouse** | 大中型, 多源异构数据 | 灵活+治理兼顾 | 技术栈复杂 |
| **Data Mesh** | 大规模, 多个BU各有独立数据团队 | 扩展性好, BU自主 | 治理成本高, 重复建设风险 |

**推荐演进路径(大多数企业):**
```
集中DW → Lakehouse → 有条件的向Data Mesh演进(不是一定要到Mesh)
```

### 第五步: 数据质量与主数据管理

#### 5.1 数据质量度量

4个核心质量维度 (精确版):

| 维度 | 定义 | 度量公式 | 目标 |
|------|------|---------|------|
| 完整性 | 没有缺失的必要字段 | 完整记录数/总记录数 | >99% |
| 准确性 | 数据反映真实世界 | 准确记录数/抽样数 | >99.5% |
| 一致性 | 同一数据在不同系统一致 | 一致记录数/应有同样值的记录数 | >98% |
| 及时性 | 数据在需要时可获取 | 在规定时间内到达的记录数/总记录数 | >99%(实时>99.9%) |

#### 5.2 主数据管理(MDM)实施策略

**MDM四模式选择:**

| 模式 | 说明 | 适用场景 |
|------|------|---------|
| **Registry** (注册表) | 只存链接, 不存实际数据 | 需要快速识别"谁是谁", 不改源系统 |
| **Coexistence** (并存) | MDM Hub存部分属性, 源系统保留完整数据 | 逐步过渡方案 |
| **Transactional** (事务型) | MDM Hub=唯一权威来源, 所有系统读写Hub | 源系统众多, 数据质量差, 有决心治理 |
| **Consolidated** (集中型) | 从源系统汇聚成一个黄金记录供查询 | 报表/分析场景, 不需要写回源系统 |

**实施步骤:**
1. 选1-2个最痛的主数据域(首选客户/产品)
2. 定义该域的主数据模型(哪些属性, 来源在哪, 谁说了算)
3. 做一次全量匹配+去重+合并
4. 建立持续的去重与合并规则
5. 发布给消费系统(通过API或ETL)

### 第六步: 数据路线图

```
Phase 1: Foundation (0-6月)
├── 建立数据治理委员会 + 任命首批数据Owner
├── 选2个数据域(如客户+产品), 定义数据标准
├── 数据平台基础搭建(Lakehouse)
├── 首个数据质量仪表盘上线(监控1-2个核心系统)
└── 里程碑: 首个数据域的数据标准发布, 首个用例的数据接入完成

Phase 2: Scale (6-12月)
├── 扩展到全业务域的数据标准
├── 主数据管理(MDM)上线(第1个域)
├── 数据目录(Data Catalog)上线: 所有核心数据集可发现
├── 自助BI平台+数据素养培训(100+人)
└── 里程碑: MDM第一域上线, 数据资产100%可发现

Phase 3: Innovate (12-24月)
├── 实时数据管道(核心场景)
├── 数据产品概念引入(Data as a Product)
├── AI/ML平台与数据平台深度对接
├── 数据价值仪表盘(量化数据对业务的贡献)
└── 里程碑: 数据驱动的收入占比可量化
```

## 质量检查
- [ ] 数据治理组织不是"架空的": 每个数据Owner有具体的人名和职责
- [ ] 数据标准不是"字典厚得像辞海但没人看": 从2-3个最痛的数据元素开始
- [ ] 平台选型有明确理由, 对比了替代方案
- [ ] 数据质量目标有基线和目标值(不是"要提高数据质量")
- [ ] 考虑了行业合规要求
- [ ] 路线图第一阶段有Quick Win(数据战略最忌讳"先建平台等3年")

## 常见陷阱

| 陷阱 | 为什么错 | 正确做法 |
|------|---------|---------|
| "先建大数据平台" | 建好平台没有数据接入=豪华商场没有商铺 | 用例驱动: 每个阶段的数据接入以一个具体业务用例为锚 |
| 数据治理=IT的事 | 数据Owner应该来自业务, IT是技术支持 | 从第一天就让业务VP当数据Owner, 让他们为"自己的数据"负责 |
| 追求完美数据质量 | "数据必须100%准确才敢用" → 永远上不了线 | 不同场景不同质量要求: AI推荐可容忍噪声, 财务报告零容忍 |
| 数据标准变成字典 | 几百页的PDF, 写完没人看 | 数据标准嵌入数据平台(自动化校验, 不通过不让人写入) |
| 忽略数据文化 | 技术搭好了, 没人用, 业务继续用Excel | 数据素养培训+Treat data as product(数据产品有SLA/文档/客服) |
