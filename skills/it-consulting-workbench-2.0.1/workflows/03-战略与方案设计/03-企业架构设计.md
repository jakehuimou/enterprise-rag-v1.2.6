# 企业架构设计 (Enterprise Architecture Design)

## 目标

基于TOGAF ADM框架,完成企业架构的现状(As-Is)建模与目标(To-Be)设计,产出架构定义文档与差距分析。

---

## 前置条件
- IT现状诊断报告已完成
- IT战略方向已获初步共识
- 关键利益相关者已识别并可参与架构评审

## 输入物
- IT现状诊断报告 (来自workflow 02-04)
- IT战略规划初稿 (来自workflow 03-01)
- 业务能力模型/业务战略文档
- 现有架构文档(如有)

---

## 操作步骤

### 第一步: 架构范围确定 (Architecture Scope)

**产出**: 架构范围声明 (Architecture Scope Statement)

1. **明确架构工作范围**
   - 全企业?某个业务域?某个产品线?
   - 影响哪些部门/哪些系统/哪些流程?
   - 排除什么?

2. **确定架构维度**
   - 业务架构 (Business Architecture) — 必选
   - 数据架构 (Data Architecture) — 必选
   - 应用架构 (Application Architecture) — 必选
   - 技术架构 (Technology Architecture) — 必选
   - 安全架构 — 视项目范围而定

3. **架构范围声明模板**
| 要素 | 内容 |
|------|------|
| 架构范围 | [如: 中国区核心业务系统, 不含海外子公司] |
| 时间范围 | 现状(As-Is) → 目标(To-Be, 3年后) |
| 业务领域 | [如: 交易/风控/客服/财务] |
| 关键约束 | [如: 核心系统不能停机, 数据不能出境, 预算上限] |
| 排除事项 | [如: 办公网络, 非核心边缘系统] |

---

### 第二步: 业务架构设计 (Business Architecture)

**产出**: 业务能力地图 + 业务流程图 + 组织映射

#### 2.1 业务能力建模

构建L1→L2→L3的业务能力地图:

```
Level 1: 战略能力
  ├── 市场洞察
  ├── 产品创新
  └── 战略规划

Level 1: 核心能力
  ├── 市场与销售
  │   ├── L2: 营销管理
  │   │   ├── L3: 活动策划
  │   │   ├── L3: 线索管理
  │   │   └── L3: ROI分析
  │   └── L2: 销售管理
  │       ├── L3: 商机管理
  │       ├── L3: 报价管理
  │       └── L3: 合同管理
  ├── 产品交付
  │   └── ...
  └── 客户服务
      └── ...

Level 1: 支撑能力
  ├── 财务与会计
  ├── 人力资源
  ├── IT管理
  └── 法务与合规
```

**能力热度图 (Capability Heatmap)评估维度:**
- 战略重要性: 1(低) — 5(关键)
- 当前成熟度: 1(手工) — 5(世界级)
- IT覆盖度: 1(无系统支撑) — 5(全自动化)
- 竞争差异度: 通用能力 / 差异化能力 / 核心竞争力

**热度图输出格式:**
| 业务能力 | 战略重要性 | 当前成熟度 | IT覆盖度 | 差距(重要性-成熟度) | 改进优先级 |
|---------|----------|----------|---------|-----------------|----------|
| 客户360视图 | 5 | 2 | 1 | 3 | 高 |
| 智能定价 | 4 | 1 | 1 | 3 | 高 |
| 财务报表 | 3 | 4 | 4 | -1 | 低 |

#### 2.2 价值流映射

选1-3个核心价值流画端到端流程:

```
价值流: 从订单到收款 (Order-to-Cash)

[客户下单] → [信用审核] → [订单确认] → [仓储分拣] → 
[物流配送] → [客户签收] → [开票] → [收款核销]

每个节点标注:
- 当前痛点: [如: 信用审核手工, 耗时2天]
- 当前系统: [如: Excel + Email]
- 目标状态: [如: 自动信用评分, <5分钟]
- 改进杠杆: [如: 规则引擎 + 外部征信API]
```

#### 2.3 组织映射

业务能力 → 负责部门 → 支撑应用 → 关键角色:

| 业务能力 | 负责部门 | 支撑应用 | 业务Owner | IT Owner |
|---------|---------|---------|----------|---------|
| 客户360视图 | CRM部 | Salesforce | 张总 | IT李经理 |
| ... | | | | |

### 第三步: 数据架构设计 (Data Architecture)

**产出**: 数据实体关系图 + 数据流图 + 数据治理要求

#### 3.1 主题域模型 (Subject Area Model)

识别数据主题域并建立高层关系:

```
客户域       产品域       交易域       风险域
  │            │            │            │
  ├─ 客户主数据 ├─ 产品目录   ├─ 订单      ├─ 信用评分
  ├─ 客户画像   ├─ 定价      ├─ 支付      ├─ 欺诈标记
  ├─ 客户偏好   └─ 库存      ├─ 履约      ├─ 合规审计
  └─ 客户交互               └─ 结算      └─ 监管报告

跨域数据流: 客户域 → 交易域 → 风险域 → 客户域 (反馈)
```

#### 3.2 数据架构三要素

| 维度 | As-Is痛点 | To-Be设计 | 迁移策略 |
|------|----------|----------|---------|
| 主数据管理(MDM) | 客户数据5个系统各一套 | 统一MDM, 一次录入全链路同步 | 先选客户/产品两个域, 试点后再推广 |
| 数据集成层 | 点对点接口, N*(N-1)爆炸 | ESB/API Gateway + 事件驱动 | 逐步从点对点迁移到总线路由 |
| 数据分析层 | BI报表各自为政 | Lakehouse + 语义层 + 统一BI | 先建数仓底座, 再迁移存量报表 |

#### 3.3 数据治理简要设计

- 数据Owner: 每个主题域指定业务Owner
- 数据标准: 主数据编码规则/元数据标准/数据字典
- 数据质量: 完整/准确/一致/及时/唯一 5维度量
- 数据安全: 分级分类(公开/内部/机密/绝密)

### 第四步: 应用架构设计 (Application Architecture)

**产出**: 应用全景图 + 应用交互矩阵 + 应用分类与处置建议

#### 4.1 应用分类 (Gartner Pace-Layered)

| 层级 | 定义 | 特征 | 生命周期 | 技术策略 |
|------|------|------|---------|---------|
| **SoR** (System of Record) | 记录系统: ERP/核心银行/HIS | 稳定,严格管控,长周期 | 10-20年 | 现代化/包裹化/逐步替换 |
| **SoD** (System of Differentiation) | 差异化系统: CRM/风控/定价引擎 | 中等变化,支撑竞争力 | 3-7年 | 重构/解耦为微服务 |
| **SoI** (System of Innovation) | 创新系统: AI推荐/数字孪生 | 快速迭代,试验性 | 1-2年 | 新建/云原生/快速试错 |

#### 4.2 应用合理化 (Application Rationalization)

对每个应用标注处置建议:

```
应用: [名称]
├── 类型: SoR / SoD / SoI
├── 业务适配度: 高/中/低
├── 技术健康度: 高/中/低
├── 处置建议: 保留 / 升级 / 替换 / 退役 / 合并
├── 理由: [1-2句]
├── 预计投入: $[X]M
└── 时间窗口: [YYYY-QX] — [YYYY-QX]
```

处置矩阵:

| | 业务适配度高 | 业务适配度中 | 业务适配度低 |
|---|---|---|---|
| **技术健康度高** | 保留+持续优化 | 待观察 | 调查替代方案 |
| **技术健康度中** | 升级/重构 | 结合其他因素判断 | 替换/退役 |
| **技术健康度低** | 现代化/包裹化 | 替换(计划内) | 立即退役 |

#### 4.3 应用集成架构

绘制应用间的主要交互关系:

```
渠道层: [手机App] [Web] [小程序] [门店终端] [API合作伙伴]

        ↓ 统一API Gateway ↓

业务中台: [订单中心] [用户中心] [商品中心] [库存中心] [营销中心]
                ↕ 事件总线(Event Bus) ↕
数据中台: [数据采集] → [数据加工] → [数据服务] → [数据应用]

        ↓ 集成层 ↓

后台系统: [ERP] [财务] [HR] [OA] [SCM]
```

### 第五步: 技术架构设计 (Technology Architecture)

**产出**: 技术平台蓝图 + 技术选型建议 + 技术标准与原则

#### 5.1 技术平台蓝图

定义目标技术平台的逻辑分层:

```
┌──────────────────────────────────────────┐
│          安全与合规层 (贯穿全栈)             │
├──────────────────────────────────────────┤
│  用户体验层: Portal / Mobile / Web         │
├──────────────────────────────────────────┤
│  API & 集成层: API Gateway / ESB / Event Bus│
├──────────────────────────────────────────┤
│  业务服务层: 微服务(容器化) / Serverless     │
├──────────────────────────────────────────┤
│  数据服务层: Lakehouse / MDM / Feature Store│
├──────────────────────────────────────────┤
│  AI/ML平台层: MLOps / LLMOps / Agent框架   │
├──────────────────────────────────────────┤
│  基础设施层: 多云/混合云 / IaC / 可观测性     │
├──────────────────────────────────────────┤
│  治理与运维层: CMDB / ITSM / FinOps / DevOps│
└──────────────────────────────────────────┘
```

#### 5.2 关键技术选型决策(非供应商选择, 留到阶段3)

| 技术领域 | 战略方向 | 理由 | 约束 |
|---------|---------|------|------|
| 云策略 | 混合云(AWS+私有云) | 核心数据保留在私有云 | 数据出境合规 |
| 容器编排 | Kubernetes | 行业标准, 人才供给充足 | — |
| API管理 | Kong / APISIX | 开源+高性能 | 需自建运维能力 |
| 数据库 | PostgreSQL + Redis + MongoDB | OLTP+缓存+文档 | — |
| 消息中间件 | Kafka | 高吞吐+事件溯源 | 运维成本高 |
| CI/CD | GitHub Actions + ArgoCD | 云原生GitOps | — |
| 可观测性 | Grafana + Prometheus + OpenTelemetry | 开源标准 | — |

#### 5.3 技术原则 (Architecture Principles)

格式: `原则名: 一句话原则 → 理由 → 影响`

1. **云优先**: 新应用默认使用云服务(PaaS优先于IaaS) → 降低运维负担, 弹性伸缩 → 需云技能建设
2. **API First**: 所有系统间通信通过API → 松耦合, 可替换 → 需API治理
3. **安全左移**: 安全评审从架构设计阶段开始 → 降低后期修复成本 → 可能减缓初期开发速度
4. **数据作为资产**: 数据集中管理, 所有权在业务 → 打破数据孤岛 → 需数据治理投入
5. **自动化一切**: 可自动化的手动过程不手工做 → 降低人为错误 → 初期投入较高

### 第六步: 目标架构共识 (Architecture Review)

#### 6.1 架构评审会 (Architecture Review Board, ARB)

**参会者**: CIO + 业务VP代表 + IT架构负责人 + 安全负责人 + 数据负责人

**议程 (90分钟)**:
1. 架构范围与原则重申 (5min)
2. As-Is架构关键发现 (15min)
3. To-Be架构设计 (30min): 业务→数据→应用→技术
4. 关键架构决策点讨论 (20min): 5-7个需要决策的架构问题
5. 差距分析与迁移路径 (10min)
6. 下一步与行动项 (5min)
7. 决策记录 (5min)

#### 6.2 架构决策记录 (ADR)

每个关键决策填写一张ADR:

```
ADR-[序号]: [标题]

背景: [为什么需要做这个决策?]
决策: [具体做了什么决定?]
替代方案: [考虑过什么其他方案? 为什么没选?]
影响: [这个决定的积极影响 + 负面后果]
状态: 提议 / 已批准 / 已实施 / 已废弃
日期: [YYYY-MM-DD]
决策者: [姓名/角色]
```

### 第七步: 差距分析 (Gap Analysis) 与迁移路径

#### 7.1 差距矩阵

| 架构域 | As-Is | To-Be | 差距描述 | 填补方式 | 优先级 | 预估投入 |
|--------|-------|-------|---------|---------|--------|---------|
| 业务: 智能定价 | 手工Excel | AI动态定价引擎 | 无数据/无算法/无系统 | 新建 | 高 | $2M |
| 数据: 客户360 | 5个客户表, 无关联 | 统一MDM+CDP | 数据标准/集成/治理 | 改造 | 高 | $1.5M |
| 应用: 旧ERP | 15年前Oracle EBS | SaaS ERP | 10年技术债 | 替换 | 中 | $5M |
| 技术: 容器化 | 虚拟机部署 | Kubernetes | 运维/监控/流程 | 升级 | 中 | $0.5M |

#### 7.2 迁移路线图

```
Wave 1 (0-6月): 基础就绪
├── API Gateway部署
├── CI/CD Pipeline搭建
├── 第一个微服务试点(选低风险场景)
└── 数据平台基础搭建

Wave 2 (6-18月): 核心迁移
├── SoD系统微服务化改造(2-3个系统)
├── 主数据管理(MDM)一期上线
├── 容器化迁移(30%工作负载)
└── 事件驱动架构试点

Wave 3 (18-30月): 规模化
├── SoR系统包裹化
├── 全量容器化(80%+工作负载)
├── AI平台整合进架构
└── 全链路可观测性上线

Wave 4 (30-36月): 优化与创新
├── 自动化治理
├── Agentic AI集成
└── 架构持续演进机制
```

## 常见陷阱

| 陷阱 | 为什么错 | 正确做法 |
|------|---------|---------|
| "纸上建筑" | 架构设计与实际落地脱离 | 每个To-Be设计都标注第一个落地系统名称 |
| 过度设计 | "我们要建一个支持100亿并发的中台" — 实际日活2000 | 按3年业务规模设计, 预留扩展点, 不提前构建 |
| 架构评审是投票制 | 10个人评审, 每人提一条, 最后谁也说不清为什么这样 | 明确架构Owner, 评审是"提意见/发现风险", 不是"替架构师做决定" |
| 忽略存量系统的人力依赖 | "这个系统太老了, 换掉" — 但只有老李一个人懂它, 老李快退休了 | 优先处理关键人物依赖的系统, 隐性知识挖掘要排在退役之前 |
| 技术选型追新 | "用最新最热的技术" — 团队没人会用, 招不到人 | 评估"团队能驾驭 + 社区活跃 + 供应商稳定"三角 |
