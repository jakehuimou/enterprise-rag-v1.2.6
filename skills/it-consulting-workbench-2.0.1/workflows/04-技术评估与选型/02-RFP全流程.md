# RFP全流程 (Request for Proposal — End to End)

## 目标

从需求定义到RFP发出、供应商答疑、提案回收的全流程管理, 确保RFP质量(供应商能看懂、能回应、方便对比)。

---

## 前置条件
- 技术选型/采购需求已获内部批准
- 预算范围已确定
- 关键评估标准已获利益相关者一致同意
- 已决定用RFP(而非直接谈判/单一来源)

## 输入物
- 业务需求文档/技术需求列表
- 采购策略 (竞标/议价/单一来源的选择)
- 供应商长名单
- 预算上限 + 时间表

---

## 操作步骤

### 第一步: 供应商长名单建立

#### 1.1 供应商初步筛选来源

| 来源 | 适用场景 |
|------|---------|
| Gartner Magic Quadrant / Forrester Wave | 企业软件(SaaS/ERP/CRM等) |
| 行业口碑/同行推荐 | 实施服务/专业服务 |
| 开源社区活跃度 | 开源技术选型 |
| 合作伙伴生态系统 | 选择生态内供应商(如SAP/云厂商生态) |
| 咨询公司自身经验 | 团队实战经验 |

#### 1.2 长名单筛选为短名单 (3-5家)

筛选标准:
- 功能覆盖度: 满足核心需求的 >80%
- 行业案例: 在同行业有3+个类似规模案例
- 本地支持: 在客户所在地区有服务团队
- 财务稳定: 不会2年内倒闭(看融资/上市公司财报/现金流)
- 文化匹配: 与客户的文化/工作方式是否兼容

**筛选模板:**
| 供应商 | 功能 | 行业案例 | 本地支持 | 财务 | 文化 | 初筛结果 |
|--------|------|---------|---------|------|------|---------|
| A | 85% | 5案例 | 有(50人) | 上市公司 | 匹配 | ✅短名单 |
| B | 70% | 1案例 | 无(海外) | B轮 | 未知 | ❌不邀请 |
| C | 90% | 10案例 | 有(200人) | 上市公司 | 匹配 | ✅短名单 |
| D | 88% | 3案例 | 有(20人) | 盈利 | 匹配 | ✅短名单 |

**短名单数量**: 3-5家 (少于3家=竞争不充分, 多于5家=评估成本太高)

---

### 第二步: RFP文档编写

#### 2.1 RFP文档结构

完整的RFP文档应包含以下章节:

```
第一章: 项目概述
├── 公司介绍: 1-2段, 客户做什么的
├── 项目背景: 为什么要做这个项目
├── 项目目标: 具体要达成什么(量化)
├── 项目范围: 包含什么, 不包含什么
└── RFP时间表: 关键日期

第二章: 业务需求
├── 业务场景描述(用业务语言, 不是技术语言)
├── 当前痛点(是什么, 为什么现在必须解决)
└── 期望的业务成果(量化)

第三章: 技术要求 (详细程度: 宁多勿少)
├── 功能需求(按优先级: 必须有/应该有/可以有)
├── 非功能需求(性能/安全/可用性/扩展性)
├── 集成需求(与哪些系统对接, 什么协议)
├── 数据需求(数据量/格式/迁移/驻留)
├── 技术环境(现有技术栈, 约束条件)
└── 安全与合规需求

第四章: 供应商资质要求
├── 公司资质(成立时间/规模/财务状况)
├── 行业经验(同行业案例, 含客户可联系的)
├── 实施能力(团队规模/方法论/认证)
├── 支持服务(SLA/响应时间/升级流程)
└── 合作伙伴关系(如有)

第五章: 实施与项目要求
├── 预期时间表
├── 实施方法论要求
├── 培训与知识转移要求
├── 变革管理要求
└── 验收标准(写得越具体, 后期争议越少)

第六章: 商务要求
├── 报价结构(要求按什么维度报价, 方便横向对比)
├── 付款条件(期望)
├── 合同条款关键要求
└── 知识产权/数据归属

第七章: 评选流程与标准
├── 评选阶段(书面→演示→PoC→谈判)
├── 评选维度与权重(透明公开)
├── 提案格式要求(页数/格式/语言/截止时间)
└── 联系方式与答疑流程

第八章: 附录
├── 术语表
├── 现有技术环境详解
└── 数据样本(脱敏)
```

#### 2.2 关键注意事项

**功能需求书写标准:**
```
❌ 差: "系统要支持用户管理"
✅ 好: "系统需要支持至少50万用户的账户管理, 包括:
     - 用户注册(手机号+邮箱+第三方账号)
     - 角色与权限管理(至少支持5级自定义角色)
     - 用户生命周期管理(创建→激活→冻结→注销)
     - 批量导入/导出(单次>10万条, <5分钟)
     - 登录安全(支持MFA/异常登录检测/多次失败锁定)"

原则: 每个需求都可以被验证"供应商有没有做到"
```

**报价表标准化(强制):**
在RFP中附上统一格式的报价模板, 这是横向对比的关键:

```
供应商名称: [_________]

一、软件许可证 (年度/订阅)
  1.1 核心平台许可: [$____] x [____] 用户 = $[____]
  1.2 附加模块: [$____] x [____] = $[____]
  ...

二、实施服务 (一次性)
  2.1 项目管理: [____]人天 x $[____] = $[____]
  2.2 配置/开发: [____]人天 x $[____] = $[____]
  2.3 测试: [____]人天 x $[____] = $[____]
  2.4 培训: [____]人天 x $[____] = $[____]
  ...

三、年度维护/支持
  3.1 标准支持(5×8): $[____]/年
  3.2 高级支持(7×24): $[____]/年
  ...

四、其他费用 (请逐项列出)
  ...

5年总拥有成本(TCO)汇总:
  Year 1: $[____]
  Year 2: $[____]
  Year 3: $[____]
  Year 4: $[____]
  Year 5: $[____]
  5年总计: $[____]
```

### 第三步: RFP时间表制定

**标准RFP时间表 (通常8-12周):**

| 阶段 | 时间 | 活动 |
|------|------|------|
| RFP发出 | Week 1 Day 1 | 邮件正式发送给短名单供应商 |
| 供应商确认参与 | Week 1 Day 3 | 供应商回复是否参与 |
| 供应商书面提问截止 | Week 2 Day 5 | 所有问题通过正式渠道提交 |
| 客户发布答疑(给所有供应商) | Week 3 Day 3 | 统一答复, 所有供应商看到的是一样的 |
| 提案提交截止 | Week 5 Day 5 | 严格截止, 迟交不收 |
| 第一阶段评估(书面) | Week 6-7 | 按评分卡打分, 选出2-3家进入演示 |
| 供应商演示 | Week 8 | 每家2-3小时, 同一议程 |
| 第二阶段评估(演示) | Week 9 | 更新评分, 选出1-2家进入PoC |
| PoC/试用 | Week 10-12 | 限时+限范围+明确的Go/No-Go标准 |
| 最终评估与谈判 | Week 13+ | 综合评分, 进入合同谈判 |

### 第四步: 供应商答疑管理

#### 4.1 答疑原则

```
规则:
1. 所有问题通过正式渠道(邮件/RFP系统)提交, 不接受口头/微信/电话提问
2. 所有供应商收到的问题和答案完全一致(匿名化后群发)
3. 答疑文档是RFP的正式补充, 与RFP正文具有同等效力
4. 如果发现RFP中确实有遗漏/错误, 通过"澄清/补遗"正式修正
```

#### 4.2 答疑文档模板

```
RFP答疑 — 第[X]批

以下问题和答复适用于所有收到本RFP的供应商。

Q1: [供应商问题原文(匿名化)]
A1: [客户答复]

Q2: [供应商问题原文(匿名化)]
A2: [客户答复]

...

补充/澄清:
- 原RFP第X章第Y节, [修改内容]
- ...

发布日期: [YYYY-MM-DD]
```

---

### 第五步: 提案回收与合规检查

#### 5.1 提案接收检查清单

```
□ 在截止时间前收到的? (迟交=拒收, 这条规矩不能破)
□ 按要求的格式提交的? (PDF/装订/数量)
□ 所有必填部分都有? (报价表/案例清单/团队介绍/...)
□ 报价在预算范围内? (如果超出, 是否显著超出, 可考虑直接淘汰)
□ 有明确的接受/不接受/例外条款? (如果不接受RFP核心条款, 必须标记)
□ 有供应商资质/案例支撑?
```

#### 5.2 不符合要求的处理

```
迟交: 一律拒收 (除非有不可抗力且有证据, 且对所有供应商公平)
格式不符: 给24小时补正(仅格式, 内容不能改)
缺少关键报价: 要求24小时内补充, 否则不进入评分阶段
不接受核心条款: 可进入评分, 但必须在评分中反映(作为风险扣分)
```

## 交付物
1. **供应商长名单 → 短名单筛选记录**
2. **RFP完整文档** (使用 templates/RFP需求建议书模板.md)
3. **标准报价表** (发给供应商)
4. **答疑记录** (多批)
5. **提案接收与合规检查记录**

---

## 质量检查
- [ ] RFP中的需求可验证(每个需求都能判断"做到了/没做到")
- [ ] 报价表标准化, 保证供应商报价横向可比
- [ ] 评选标准与权重在RFP中公开透明
- [ ] 答疑对所有供应商公平一致
- [ ] 时间表合理, 给供应商足够的响应时间(至少3周)
- [ ] RFP不包括任何有偏向性的语言(只许某一家能做)

## 常见陷阱

| 陷阱 | 为什么错 | 正确做法 |
|------|---------|---------|
| RFP需求太模糊 | 供应商报价完全不同, 无法横向对比, 后期争议无穷 | 花60%精力写清楚需求, 40%精力评估 |
| 邀请太多供应商 | 10家回复=评估团队累死, 每家平均花1小时=也不公平 | 短名单3-5家, 每一家都认真评估 |
| 和某一家供应商"关系好" | 提前透露信息/修改需求偏向特定产品 = 不公正, 而且可能违法 | 所有沟通通过正式渠道, 所有供应商得到一样的信息 |
| 忽视内部利益相关者 | IT选了A, 业务喜欢B, 老板朋友推荐C — 三家混战 | RFP前就搞定内部对齐, 确定评估标准和权重 |
| 不检查供应商案例 | "有10个案例" → 但可能是供应商只做了一小部分 | 要求2-3个可联系的名客户, 然后真的打电话 |
| 评分标准不透明 | 招标结束, 落选的问"为什么不是我?" 说不清楚 = 风险 | 评分卡在RFP中公布权重, 评分过程有书面记录 |
