# 供应商评估与选型 (Vendor Evaluation & Selection)

## 目标

基于RFP回复, 通过书面评估→供应商演示→PoC→参考调查→最终决策, 选出最优供应商, 产出选型决策报告。

---

## 前置条件
- RFP已发出, 提案已回收
- 评估团队已组建(业务+IT+采购+安全+法务)
- 评分标准和权重已在RFP中公布

## 输入物
- 供应商提案 (3-5份)
- 供应商标准报价表 (可横向对比)
- 评估评分卡模板 (来自 templates/供应商评分卡模板.md)

---

## 操作步骤

### 第一步: 书面提案评估

#### 1.1 组建评估委员会

| 角色 | 职责 | 投票权重 |
|------|------|---------|
| 业务Owner (主评估人) | 业务需求匹配度 | 30% |
| IT负责人 | 技术匹配度+架构 | 25% |
| CIO/IT总监 (决策人) | 战略匹配度+最终决策 | 20% |
| 采购 | 商务条款+风险 | 10% |
| 安全负责人 | 安全合规 | 10% |
| 法务 | 合同风险 | 5% |

#### 1.2 独立评分 (先各自打分, 再汇总讨论)

**纪律:**
- 每个评估人先独立阅读提案并打分 (不互相讨论, 避免"羊群效应")
- 打分完成后, 汇总所有人的评分
- 只有在评分差异>2分(10分制)的项目上, 才需要讨论
- 讨论后可以调整评分, 但要记录调整原因

#### 1.3 评分汇总

| 评估维度 | 权重 | 供应商A | 供应商B | 供应商C |
|---------|------|--------|--------|--------|
| 功能覆盖度 | 25% | 8.5 | 9.0 | 7.0 |
| 技术架构 | 15% | 8.0 | 8.5 | 6.0 |
| 实施能力 | 15% | 7.0 | 8.0 | 8.5 |
| 行业经验 | 10% | 9.0 | 7.0 | 6.0 |
| 公司稳定性 | 5% | 9.0 | 8.0 | 7.0 |
| 支持服务 | 10% | 7.0 | 8.5 | 8.0 |
| 总成本(TCO 5年) | 15% | 6.0(贵) | 8.0(中) | 9.0(便宜) |
| 创新/未来性 | 5% | 8.0 | 9.0 | 5.0 |
| **加权总分** | **100%** | **7.65** | **8.30** | **7.23** |

成本评分换算: (预算中位数/供应商报价) × 10, 上限10分

#### 1.4 筛选2-3家进入演示阶段

原则:
- 总分前3名 (如果第3名和第4名差距在0.5分以内, 都进演示)
- 任何一家如果在"必须满足"的需求上有Fail, 直接淘汰(不管总分)
- 单维度极端的注意: 如技术满分但实施能力3分 → 危险信号

---

### 第二步: 供应商演示评估

#### 2.1 演示日准备

**统一Agenda (每家3小时):**
```
0:00-0:30  供应商公司介绍 + 项目理解 (30min)
0:30-1:30  产品/方案演示 (60min) — 核心!
1:30-2:00  实施方法论 + 团队介绍 (30min)
2:00-2:30  客户案例分享 (30min)
2:30-3:00  Q&A (30min)
```

**必须要求:**
- 演示用真实产品, 不能只用PPT (除非你买的是PPT)
- 准备3-5个真实业务场景脚本, 让供应商现场演示如何满足
- 所有供应商演示同样的场景, 便于对比
- 供应商演示团队=以后给你做实施的团队 (不要让销售演完, 实施团队完全不同)

#### 2.2 演示评估维度

| 维度 | 评分(1-10) | 观察要点 |
|------|----------|---------|
| 产品功能 | [1-10] | 符合度+易用性+响应速度 |
| 演示准备度 | [1-10] | 是否准备充分? 场景是否切中痛点? |
| 团队能力 | [1-10] | 回答问题是否专业? 是否诚实说"不知道"? |
| 沟通理解 | [1-10] | 是否理解我们的业务? 还是讲通用PPT? |
| 灵活性 | [1-10] | 是否愿意定制? 还是"我们的产品就这样" |
| 文化匹配 | [1-10] | 想象一下和这群人一起工作18个月的心态 |

#### 2.3 演示后总结

每个评估人填写:
```
供应商: [名称]
最欣赏的: [最多3点]
最担忧的: [最多3点]
如果选这家, 最大的风险是什么?
如果选这家, 你愿意当项目的业务Sponsor吗? (是/否)
其他想法:
```

### 第三步: PoC (Proof of Concept) / 试用

#### 3.1 什么时候需要PoC?

需要PoC的情况:
- 产品在关键场景上的能力不确定
- 技术集成复杂度高
- 供应商规模小但产品创新 (需要验证能不能落地)
- 这是一个"平台"产品, 未来很多系统要依赖它

不需要PoC的情况:
- 成熟产品/行业标准(如Office 365, Salesforce)
- 已有同行业同规模成功案例
- 评估团队对产品能力高度确信
- 时间/预算不允许

#### 3.2 PoC设计

**PoC成功的5要素:**

1. **限定范围**: 1-3个最关键场景, 不是"你把整个系统搭出来试试"
2. **限定时间**: 2-4周, 不能再长(否则就是一个mini项目)
3. **明确成功标准**: 不是一个模糊的"试试看", 而是:
   ```
   PoC成功标准:
   □ 场景1: 100万用户数据导入, 时间<2小时, 数据准确率>99.9%
   □ 场景2: 核心API响应时间<200ms(P99), 并发500 QPS不降级
   □ 场景3: 与现有CRM系统完成双向数据同步, 延迟<5秒
   以上3项全部满足 = PoC通过
   1项不满足 = 可讨论是否接受(看偏差程度)
   2项不满足 = 不通过
   ```
4. **客户提供数据**: 用客户自己的(脱敏)数据, 不做假数据PoC
5. **PoC也是团队测试**: 观察供应商PoC团队的专业度/沟通/响应速度 → 这就是以后项目实施的样子

#### 3.3 PoC后决策

```
PoC结果:
├── 全部通过 → 进入最终谈判
├── 部分通过 → 分析差距是否可接受
│   ├── 可接受 → 要求供应商在合同里承诺上线前解决
│   └── 不可接受 → 淘汰或要求二次PoC
└── 未通过 → 淘汰
```

### 第四步: 参考客户调查

#### 4.1 找到真实的参考客户

不要只问供应商提供的"友好客户", 而是:
- 从供应商案例中随机选
- 通过LinkedIn/行业网络找到使用该供应商产品的同行
- 问供应商: "有没有XX行业/XX规模/最近1年内上线的客户?"

#### 4.2 参考调查提问清单

**5个必问问题:**

1. "如果可以重来, 你还会选这家供应商吗? 为什么/为什么不?"

2. "实际总成本是你初始预算的多少? (通常答案是1.5-2倍, 问清楚多了什么)"

3. "项目实施过程中最大的问题是什么? 有没有什么事是供应商答应但没做到的?"

4. "上线后, 系统稳定性怎么样? 多久出一次问题? 出了问题他们多久能解决?"

5. "他们的团队, 特别是关键人员, 稳定吗? 项目实施期间换过人吗?"

**附加问题:**
- "他们的支持/客服质量怎么样? 你找他们解决问题一般要多久?"
- "实施超时了吗? 超了多久? 什么原因?"
- "有没有什么隐藏成本是合同里没写的?"
- "如果再给你一次机会, 你会把什么条款写进合同?"

**提问技巧:**
- 电话沟通>邮件问卷 (人们更愿意在电话里说实话)
- 先建立信任: "我们都是同行, 你帮帮我, 避免踩坑"
- 如果对方含糊其辞或非常官方, 警惕 (可能签了保密协议不能说实话, 或者根本就不满意)

---

### 第五步: 最终评估与决策

#### 5.1 综合评分更新

将演示和PoC结果纳入评分:

| 阶段 | 权重 | 供应商A | 供应商B |
|------|------|--------|--------|
| 书面提案 | 40% | 7.65 | 8.30 |
| 演示评估 | 25% | 7.0 | 8.5 |
| PoC结果 | 20% | 8.0(PoC通过) | —(未做) |
| 参考调查 | 15% | 8.0 | 7.0 |
| **最终综合得分** | **100%** | **7.63** | **8.03** |

#### 5.2 决策矩阵 (不止看分数)

最终决策不仅是分数最高, 还要回答:

```
战略层面:
□ 这家供应商未来3-5年还会存在并健康发展吗?
□ 这家供应商的产品路线图与我们的IT战略方向一致吗?
□ 如果选了这家, 我们会不会被锁定(Vendor Lock-in)?

执行层面:
□ 我们内部有足够的人来管理这个供应商吗?
□ 合同谈判的主动权有多大? (唯一渠道 vs 多家可选)
□ 如果实施失败, 退出的成本有多高?

政治层面:
□ 主要利益相关者都能接受这个选择吗?
□ 有没有人有强烈的反对意见需要提前处理?
```

#### 5.3 选型决策报告

```
选型决策报告: [项目名称]

1. 评估概述
   - 项目背景与范围
   - 参与供应商: A / B / C (D因迟交淘汰)
   - 评估过程: 书面(Week1-2) → 演示(Week3) → PoC(Week4-6) → 参考调查(Week5)

2. 综合评估结果
   | 供应商 | 书面(40%) | 演示(25%) | PoC(20%) | 参考(15%) | 总分 |
   |--------|----------|----------|---------|----------|------|
   | A      | ...      | ...      | ...     | ...      | ...  |
   | B      | ...      | ...      | ...     | ...      | ...  |

3. 关键差异化因素
   - 供应商A的核心优势: ...
   - 供应商A的主要风险: ...
   - 供应商B的核心优势: ...
   - 供应商B的主要风险: ...

4. 建议
   - 建议选择: 供应商[__]
   - 理由: [1-2段]
   - 关键谈判要点: ...
   - 实施关键风险与缓解: ...

5. 决策记录
   - 评估委员会成员签名
   - 最终决策人签名
   - 日期
```

## 质量检查
- [ ] 每个评估人独立打分, 有书面记录
- [ ] 成本计算考虑5年TCO, 不只是第一年
- [ ] 至少联系了2家参考客户且是真实对话(不是邮件问卷)
- [ ] PoC有明确的成功/失败标准, 且在做之前就定义了
- [ ] 最终决策有完整的书面记录(包括为什么没选其他家)
- [ ] 法务已审查关键条款(aspects of the vendor contract)

## 常见陷阱

| 陷阱 | 为什么错 | 正确做法 |
|------|---------|---------|
| 销售演示=产品能力 | 演示环境是精心准备的, 数据是干净的, 网络是独享的 | 要求用你自己的数据(脱敏)做PoC, 在真实环境中跑 |
| 只看功能,不看团队 | 买了最好的产品, 但实施团队是外包实习生 | 在合同中锁定核心团队名单, 实施期间不得随意更换 |
| 不打电话做参考调查 | 供应商给你的"友好名单"只会说好话 | 打听到真正的客户, 电话聊(不是发问卷); 问"如果可以重来" |
| 被低价吸引 | 第一年报价特别低, 第3-5年续费翻倍 | 看5年TCO, 看续费条款, 看隐性成本(定制/集成/培训) |
| 过度依赖Gartner | Gartner象限是付费参与的, 不是客观评测 | 结合同行口碑+PoC+参考调查, 形成独立判断 |
| 决策拖延 | "再评估一家"→"再看看"→项目窗口期过了 | 设定明确的决策日期, 在此之前做决定 |
