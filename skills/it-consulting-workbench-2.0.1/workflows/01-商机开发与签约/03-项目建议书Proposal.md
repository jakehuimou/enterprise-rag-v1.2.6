# 03 — 项目建议书(Proposal)

## 目标
将前期诊断和理解转化为一份赢得项目的正式建议书。Proposal的核心任务是回答客户心中三个问题: "你理解我的问题吗?你的方案可行吗?为什么选你?"

## 前置条件
- 已完成至少1-2次客户深度沟通
- 已产出问题诊断摘要
- 已了解客户预算量级和决策流程
- 已了解竞争对手(如果客户透露的话)

## 输入物
- 问题诊断摘要
- 客户会议纪要
- 客户提供的RFP(如有)
- 行业benchmark数据

---

## 操作步骤

### Step 1: 确定Proposal策略 — 写之前先想清楚三件事

**1. 谁是真正的决策者?**

```
决策人类型          他们关心什么                       Proposal怎么打
──────────────────────────────────────────────────────────────────
CEO/业务Sponsor     业务成果、竞争优势、股价/估值       执行摘要+ROI+风险
CIO/CTO             技术可行性、团队能力、架构长期性    方法论+团队+技术深度
CFO/采购             总价、性价比、付款条件、供应商风险   TCO+基准对比+付款方案
业务VP              自己部门的获益、对日常工作的影响     业务场景+变革管理
```

**2. 客户的预算级别是?**
- >$1M: 需要完整的Proposal + 现场答辩
- $200K-$1M: 精简Proposal + 1-2次深入讨论
- <$200K: 3-5页方案摘要 + 报价单

**3. 这个项目对客户是'维生素'还是'止痛药'?**
- 止痛药(合规要求/安全事故/CEO直接指令): 强调速度+确定性+风险控制
- 维生素(提效/创新/竞争力): 强调ROI+行业趋势+标杆案例

### Step 2: Proposal标准结构

```
封面页
  ├── 项目名称
  ├── 客户公司Logo + 客户名
  ├── 你的公司Logo
  ├── 日期
  └── 密级(Confidential)

第一章: 执行摘要 (Executive Summary) — 1页
第二章: 我们对客户情境的理解 (Situation Understanding) — 1-2页
第三章: 我们的方法与路径 (Our Approach) — 2-4页
第四章: 项目范围与交付物 (Scope & Deliverables) — 1-2页
第五章: 项目团队 (Our Team) — 1-2页
第六章: 时间计划 (Timeline) — 1页
第七章: 投资与商务 (Investment & Commercials) — 1-2页
第八章: 为什么选择我们 (Why Us) — 1页
第九章: 下一步 (Next Steps) — 0.5页
附录
```

### Step 3: 逐章写作指南

**第一章: 执行摘要 — 最重要的一页**

Bad:
> "XX公司是一家领先的XX企业，面临着数字化转型的挑战。我们建议进行IT战略规划..."

Good:
> "XX公司的核心ERP系统已运行12年，平均需求响应时间为4个月，而行业领先者为2周。如果不采取行动，预计未来3年因上市速度落后将损失$15-20M的市场份额。我们建议采用分阶段现代化方案，投资$3.2M，12个月内将需求响应时间缩短到4周，24个月内达到1周。对比'不改变'情景，5年净收益不低于$12M。"

核心公式: **Problem(量化痛点) → Solution(明确方向) → Impact(可衡量收益) → Credibility(为什么是我们)**

**第二章: 我们对客户情境的理解**

这是体现"你懂我"的关键章节。结构:

```
2.1 行业趋势与挑战
  [客户行业的3-5个关键趋势，每个1-2句 + 对客户的影响]

2.2 客户的业务战略与IT含义
  业务战略            →          IT含义
  "3年进入5个新市场"   →         需要可快速复制的基础架构和核心系统
  "通过M&A实现增长"    →         需要灵活的集成架构和可插拔的系统

2.3 我们理解的核心挑战
  [3-5个核心挑战，每个: 现象→业务影响→如果不解决的后果]

2.4 我们与客户的对话轨迹
  [简述你们之间到目前为止的交流，体现已经被深度卷入]
```

**第三章: 我们的方法与路径**

这是展现方法论严谨性的章节:

```
3.1 整体方法论框架
  [1张图展示整体方法: Phase 1→2→3→4]

3.2 每个阶段的具体活动、产出、时间
  阶段1: [名称 & 目标]
    关键活动: [5-8项]
    产出物: [列出]
    客户需要参与的事项: [列出，管理期望]
    时间: [_]周

  阶段2: [同结构]
  ...

3.3 与同类项目的方法论差异
  [1-2个不同点，不是贬低别人，是展示独特思考]
  如: "大多数咨询公司在AI转型中先建技术平台，我们坚持从3-5个可量化ROI的用例入手"
```

**第四章: 项目范围与交付物**

```
In Scope:
  ├── [交付物1: 名称 + 简要描述]
  ├── [交付物2: 名称 + 简要描述]
  └── [...]

Out of Scope (明确排除, 防止范围蔓延):
  ├── [不包含的内容1 + 简要原因]
  ├── [不包含的内容2 + 简要原因]
  └── [...]

假设条件 (如果这些假设不成立，范围/时间/费用可能需调整):
  ├── 客户关键人员在项目期间投入不少于X天/周
  ├── 客户在项目启动后2周内提供X数据
  ├── 客户IT团队配合完成技术环境访问
  └── [...]
```

**第五章: 项目团队**

```
[照片/姓名/Title/角色/相关经验]

团队结构图:
     ┌─────────────┐
     │ 合伙人/总监  │ ← 战略指导+质量把关+高管层沟通
     └──────┬──────┘
     ┌──────┴──────┐
     │  项目经理    │ ← 日常管理+客户PM对接+风险管控
     └──────┬──────┘
  ┌───┴───┬───┴───┬───┐
  │       │       │   │
[专家1] [专家2] [专家3] [...] ← 领域深度

每个团队成员:
- 角色: [e.g. 云架构专家]
- 相关经验: [2-3个高度相关的项目经验，含客户名/项目规模/成果]
- 投入比例: [X%] (体现真实投入，不是挂名)
```

**第六章: 时间计划**

```
阶段             W1-W2  W3-W4  W5-W6  W7-W8  W9-W10  W11-W12  W13-W14  W15-W16
启动与诊断         ████
战略设计                   ████  ████
方案细化                               ████   ████
交付物撰写                                        ████    ████
高管汇报                                                          ████
收尾与知识转移                                                           ████

★ 关键里程碑:
  W2: Kickoff & 项目章程签署
  W4: 现状诊断报告
  W8: 目标蓝图初稿评审
  W12: 最终方案评审
  W16: 董事会汇报
```

### Step 4: 定价策略

**四种定价模式:**

| 模式 | 适用场景 | 客户感受 | 风险归属 |
|------|---------|---------|---------|
| 固定价格(Fixed Price) | 范围明确、不确定性低 | 预算可预见 | 我方承担超支风险 |
| 时间与材料(T&M) | 范围模糊、探索性强 | 按实际投入付费 | 客户承担不确定性 |
| 价值导向(Value-Based) | 可清晰量化收益 | 与成果绑定 | 分享风险与收益 |
| 月度顾问(Retainer) | 长期持续支持 | 持续关系 | 双方共担 |

**报价建议:**
- 如不确定范围: 固定价格(Phase 1) + T&M(Phase 2+)
- 基础费率: 合伙人$400-600/h, 总监$300-400/h, 经理$250-350/h, 顾问$200-280/h, 分析师$150-200/h
- 以上为全球一线咨询公司参考费率，请根据地区和市场调整

**定价常见错误:**
- 为了拿项目报太低 → 后面只能派初级人员，质量下降，声誉受损
- 只报总价不给分解 → 客户没法横向比较，容易砍价
- 不设退出机制 → 项目做不下去时双方尴尬

## 交付物
1. **决策者画像**: 了解决策链和每个人的关注点
2. **项目建议书(Proposal)**: 完整的9章Proposal文档
3. **定价模型**: 在4种定价模式中选择+报价说明
4. **客户跟进计划**: Proposal发出后的跟进行动

## 质量检查

- [ ] 执行摘要可独立阅读并理解核心信息(1页内)
- [ ] "对客户情境的理解"章节能让客户说"对，这就是我们的问题"
- [ ] 方法论有逻辑，不是拼凑的框架
- [ ] Out of Scope部分与In Scope一样详细
- [ ] 团队成员经验与项目需求高度匹配
- [ ] 时间计划考虑了客户方投入和决策周期
- [ ] 定价有合理性解释(不是裸数字)
- [ ] Why Us部分不是空话("我们有经验")，而是具体匹配
- [ ] Proposal总页数不超过25页(不含附录)

## 常见陷阱

| 陷阱 | 正确做法 |
|------|---------|
| Proposal=方法论PPT的堆砌 | 客户买的是结果，不是方法论。方法论是信任基础，成果是购买理由 |
| "我们是最好的"空洞宣称 | 用具体案例代替形容词: "在XX项目我们帮客户实现了X" > "我们有丰富经验" |
| 团队名单全是合伙人，实际交付全是分析师 | 诚实标注每个人的投入比例和具体角色 |
| 不提竞争对手(假装他们不存在) | 至少暗示你知道其他选择: "相比只做技术实施，我们提供的战略+落地闭环是独特价值" |
| Proposal发出去就等回复 | 发Proposal后24小时内主动联系: "有没有什么需要我补充解释的?" |
