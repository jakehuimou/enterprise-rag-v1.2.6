# 02 — 需求澄清与问题诊断

## 目标
将客户模糊的表述（"我们的IT不行""想做AI""系统太慢了"）转化为结构化、可操作的问题陈述和初步假设。

## 前置条件
- 已完成初次客户沟通
- 已获取客户基本情况和痛点表述
- 可能已收到客户发来的背景材料

## 输入物
- 初次会议纪要
- 客户提供的背景文档（如有）
- 客户行业研究报告

---

## 操作步骤

### Step 1: 问题归类 — 5秒钟判断问题属于哪个桶

拿到客户需求后，先用以下分类框架做第一层判断：

```
客户的描述                          → 问题类别        → 核心解法方向
──────────────────────────────────────────────────────────────────
"系统太慢/老崩/不好用"              → 技术基础设施    → 现代化/云迁移/架构重构
"业务等IT开发等半年"                → 交付效率        → DevOps/平台工程/敏捷转型
"IT花了多少钱说不清"                 → IT财务管理      → TBM/FinOps/TCO建模
"竞争对手在用AI，我们也要"           → AI战略          → 成熟度评估/用例识别/路径规划
"数据各个部门都有，但用不起来"       → 数据战略        → Data Mesh/治理/平台
"系统是被收购来的，乱七八糟"         → 整合与架构      → M&A整合/EA/应用合理化
"上了ERP/CRM感觉没用起来"           → 变革与采用       → 变革管理/培训/流程再造
"不知道IT该往哪个方向走"            → IT战略规划      → 战略解码/对标/路线图
"公司被黑了/担心出事"               → 安全与风险       → NIST评估/成熟度/合规
"要选个新系统，供应商太多不知道选谁" → 供应商选型      → RFP/评分模型/PoC
"IT成本太高了被老板盯上了"          → 成本优化        → FinOps/外包评估/许可优化
"IT团队能力太差"                    → 组织人才        → 组织设计/能力模型/招聘
```

### Step 2: 问题结构化 — 用MECE进行五维分解

任何IT问题都可以从以下5个维度做MECE分解：

```
问题: [客户的原始描述]

维度1 — 技术(Technology):
  ├── 基础设施 (服务器/网络/云/存储)
  ├── 应用系统 (SoR/SoD/SoI健康度)
  ├── 数据 (质量/可访问性/治理)
  ├── 集成 (接口/中间件/API)
  └── 安全 (防护/检测/响应/合规)

维度2 — 流程(Process):
  ├── 需求管理 (怎么决定做什么)
  ├── 开发交付 (从提需求到上线的流程)
  ├── 运维管理 (变更/事件/问题/配置)
  ├── 采购与供应商管理
  └── IT治理与决策

维度3 — 组织(Organization):
  ├── IT团队结构 (集中/联邦/产品化)
  ├── 人员能力与人才梯队
  ├── 文化与协作模式
  ├── 领导力与决策效率
  └── 考核与激励机制

维度4 — 数据(Data):
  ├── 数据资产盘点与质量
  ├── 数据标准化/主数据管理
  ├── 数据治理与合规
  ├── 数据分析与AI就绪度
  └── 数据安全与隐私

维度5 — 财务(Financial):
  ├── IT总支出与营收占比
  ├── Run/Grow/Transform分配比
  ├── 单项目/单服务TCO
  ├── 外包 vs 自建支出
  └── IT投资ROI追踪
```

### Step 3: 形成问题陈述(Problem Statement)

一个好的问题陈述必须包含：**现状 + 差距 + 后果 + 时间紧迫性**

```
模板:

"[公司名]目前在[领域]方面存在[具体问题]，
与[行业领先/业务需求]相比差距为[量化差距]，
如果不解决将在[时间]内造成[商业后果]，
这需要我们在[时间框架]内通过[大致方向]来解决。"

示例:

"XX保险公司目前在核心承保系统方面存在严重技术债务——
系统基于15年前的架构，单次变更周期长达3个月，
而头部竞争对手(平安/众安)已实现周级迭代。
如果不启动现代化改造，预计在未来18-24个月内，
新产品上市速度落后将导致5-8%的保费市场份额流失。
我们需要在12个月内完成核心系统的重新平台化和微服务化。"
```

### Step 4: 生成初步假设(Initial Hypotheses)

针对问题陈述，用假设驱动方法生成3-5个可验证的假设：

```
假设模板:
"如果[假设为真]，我们应该观察到[可观测的现象]"

示例:
问题: 某零售企业线上转化率低于行业平均30%

假设1: 推荐算法数据质量不足 → 应观察到商品标签覆盖率<60%，用户画像维度<20
假设2: 技术架构性能瓶颈 → 应观察到首页加载时间>3秒(P95)，API响应>500ms
假设3: 组织协作问题 → 应观察到营销需求到上线平均超过4周，涉及5+个部门审批
假设4: 数据策略缺失 → 应观察到CDP未建设，用户行为数据采集率<50%

下一步: 优先验证假设1和3（可快速验证+影响大）
```

### Step 5: 产出 —— 问题诊断摘要

将以上步骤合成为一份1页的诊断摘要发给客户：

```markdown
# [客户公司] IT问题初步诊断摘要

## 问题陈述
[1-2段的Problem Statement]

## 问题五维分析
| 维度 | 现状评分(1-5) | 关键发现 | 影响程度 |
|------|-------------|---------|---------|
| 技术 | [评分] | [发现] | 🔴/🟡/🟢 |
| 流程 | [评分] | [发现] | 🔴/🟡/🟢 |
| 组织 | [评分] | [发现] | 🔴/🟡/🟢 |
| 数据 | [评分] | [发现] | 🔴/🟡/🟢 |
| 财务 | [评分] | [发现] | 🔴/🟡/🟢 |

## 初步假设（待验证）
1. [假设1] — 预计影响: [量化]
2. [假设2]
3. [假设3]

## 建议的下一步
- 短期(2周内): [快赢诊断动作]
- 中期(1-2月): [深入分析方向]
- 建议的咨询项目范围: [初步范围描述]

## 为什么是我们
[2-3句话说明你们做这个项目独特优势，不是卖弄，是说明匹配度]
```

## 交付物
1. **问题分类判断**: 12类问题中的哪一类/几类
2. **五维分解分析**: 技术/流程/组织/数据/财务
3. **问题陈述文档**: 问题陈述模板(方向/差距/后果/紧迫性)+初步假设
4. **客户沟通纪要**: 含即时洞察和下一步建议

## 质量检查

- [ ] 问题类别判断正确（对应上述12类之一）
- [ ] 五维分解无明显遗漏
- [ ] 问题陈述包含: 现状+差距+后果+紧迫性
- [ ] 假设是可验证的（不是不可证伪的断言）
- [ ] 诊断摘要不超过2页
- [ ] 下一步建议具体、可操作

## 常见陷阱

| 陷阱 | 正确做法 |
|------|---------|
| 客户说什么就是什么（"我们要AI"） | 追问"AI要解决什么业务问题"——可能是数据/流程/人的问题，不一定是AI |
| 诊断只聚焦技术 | 永远五维分析，10个IT问题里6个根因在流程/组织/人 |
| 太快跳到解决方案 | 假设阶段只提方向性假设，不承诺具体方案 |
| 假设不可验证（如"管理层不重视IT"） | 转化为可观测的：如"IT预算<行业均值50%且无CIO向CEO汇报" |
