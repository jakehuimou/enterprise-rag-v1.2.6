# 01 — 初次客户沟通

## 目标
在第一次与客户会议上：展示专业性、建立信任、诊断核心问题、获取足够信息推进后续工作。

## 前置条件
- 客户已同意会面（线下/线上）
- 已了解客户的基本信息（公司名/行业/规模/参会人职位）

## 输入物（会前准备）
- [ ] 客户行业研究报告（至少了解行业Top 3趋势和挑战）
- [ ] 客户公司公开信息（年报/新闻/融资/组织架构）
- [ ] 参会人LinkedIn/背景调查（知道对方关心什么）
- [ ] 类似行业/规模的项目案例整理（2-3个）

---

## 操作步骤

### Step 1: 会前48小时——准备Question List

**结构化问题清单（按顺序提问）:**

```
第一组: 建立上下文 (Context Building) — 开场15-20分钟

1. "我们想先了解一下贵司的整体情况——核心业务、最近3年的发展重点、以及您觉得未来2-3年最大的机会和挑战是什么?"
   → 目的: 理解业务全景，判断战略优先级
   → 记录重点: 他们说的"机会"和"挑战"的措辞反映了什么焦虑?

2. "目前IT/技术团队的规模和结构是怎样的?主要支撑哪些业务?"
   → 目的: 了解IT在组织中的定位（成本中心 vs 业务伙伴 vs 创新引擎）
   → 记录重点: 报告线（CIO向CEO还是CFO汇报?）

3. "过去两年在技术方面做了哪些比较大的投入或变化?"
   → 目的: 了解已投入方向和历史经验（成功/失败）
   → 记录重点: 他们在哪些项目上花了钱，哪些被叫停?

第二组: 诊断痛点 (Pain Discovery) — 20-30分钟

4. "您个人目前最头疼的技术/数字化相关的问题是什么?"
   → 目的: 找到个人层面的痛点（这个往往比"组织目标"更真实）
   → 记录重点: 他的KPIs是什么? 什么事让他在老板面前不好交代?

5. "如果这个问题不解决，会对业务产生什么影响?"
   → 目的: 量化问题的紧迫性和重要性
   → 记录重点: 这个答案可以直接用到后面的Proposal里

6. "之前尝试过解决这个问题吗?发生了什么?"
   → 目的: 了解历史尝试和原因，避免重复犯错
   → 记录重点: 之前的方案是"方案不行"还是"推行不力"?

第三组: 期望管理 (Expectation Setting) — 10-15分钟

7. "假设我们能帮您解决这个问题，什么样的结果算'成功'?"
   → 目的: 定义成功标准和可量化的KPIs
   → 记录重点: 确保成功的定义在项目开始前就清晰

8. "在决策流程上，这个项目需要哪些关键人的支持?预算大概是什么量级?"
   → 目的: 了解决策流程和预算现实
   → 记录重点: 谁是最终决策人? 预算审批需要多长时间?

9. "如果我们之后给一个初步建议，什么样的形式对您最有帮助?报告/PPT/工作坊?"
   → 目的: 了解对方的沟通偏好
   → 记录重点: 投其所好
```

### Step 2: 会议中——执行4项关键行为

**行为1: 80/20法则 — 客户说80%，你说20%**
- 第一次会议的核心目标是"听"，不是"讲"
- 只在客户需要引导时提问，不要抢话
- 你的发言控制在会议总时间的20%以内

**行为2: 在会议最后3分钟——给出一个"即时洞察"**
```
会议结束前，找一个时机说:
"基于我们刚才的讨论，我有几个初步观察，可能会对您有用——"
然后给出1-2个高质量观察。

示例:
"我注意到您提到X系统是5年前上的，但那个供应商去年已经被收购了——这可能是风险点。"
"您说的'业务部门自己买SaaS'这个现象，在制造业其实很常见，关键不是禁止，而是建立轻量治理——我看到过类似案例可以用3步解决。"

这个"即时洞察"是建立信任最有效的方式：
- 证明你听懂了
- 证明你有经验
- 给对方一个"这次会议值得"的信号
```

**行为3: 明确下一步——绝不以模糊的"回头联系"结束**
```
会议结束前必须确认:
"非常感谢您的时间。我们接下来会——
1) [具体动作]，预计[时间]给您；
2) [具体动作]，需要您这边帮忙[什么]。
您看这样合理吗？"
```

**行为4: 不过度承诺边界外的事**
```
如果客户问到你不能/不该做的:
"这个领域涉及[法律/财务审计/...]，我的专业在[IT战略/技术/...]方面，
建议这块请专业[律师/会计师/...]来评估，我可以帮您梳理需要问他们哪些问题。"
这反而增强专业可信度。
```

### Step 3: 会后24小时内——发送会议纪要和下一步

**会议纪要模板:**

```markdown
# 会议纪要 — [客户公司名] × [你的公司名]

**日期**: 202X年X月X日
**参会人**: [客户方] / [我方]
**会议目的**: 初次交流，了解客户IT/数字化需求

## 关键信息摘要
1. [核心业务和战略重点]
2. [当前的IT/数字化能力概况]
3. [识别到的3-5个关键痛点]
4. [客户对"成功"的定义]

## 我们的初步观察
1. [观察1 — MECE分类: 技术/流程/组织/数据]
2. [观察2]
3. [观察3]

## 建议的下一步
1. [具体行动1] — 我们负责，预计[时间]
2. [具体行动2] — 请客户协助，截止[时间]
3. [具体行动3] — 下次会议提议[时间/议题]

## 后续可能性(不做承诺，供参考)
- [可能的项目方向1]
- [可能的项目方向2]
```

## 交付物质量检查

会前准备:
- [ ] 已查过公司公开信息（年报/新闻/融资）
- [ ] 已查过参会人背景
- [ ] 已准备结构化问题清单（9个问题覆盖3组）
- [ ] 已准备2-3个相关案例

会后:
- [ ] 会议纪要已24小时内发出
- [ ] 纪要中有"即时洞察"内容
- [ ] 下一步行动和责任人明确
- [ ] 客户回复确认收到或表达了正面反馈

## 质量检查

- [ ] 会议目标在开会前已书面明确(发给客户)
- [ ] 三个阶段的提问清单都已准备, 每个阶段有3-5个具体问题
- [ ] 客户行业背景已提前做了功课(至少1小时研究)
- [ ] 会议中你的发言时间<40%, 客户发言>60%
- [ ] 客户至少说了2次"这个问题问得好"
- [ ] 会议纪要24小时内发出
- [ ] 纪要有明确的下一步(谁/做什么/何时)
- [ ] 纪要包含"即时洞察"——让客户觉得"这顾问是做了功课的"

## 常见陷阱

| 陷阱 | 正确做法 |
|------|---------|
| 第一次会议就推销自己的方案 | 第一次是听和诊断，解决方案在下一次 |
| 对客户说"这个简单" | 即使你觉得简单，也要说"需要评估"——轻描淡写反而让人怀疑专业性 |
| 客户问"你们做过这个行业吗?"你说"没有但..." | 诚实说没有，但马上讲"我们在类似场景做了X"或"方法论是跨行业的" |
| 为了拿项目过度承诺 | 明确边界 > 拿到项目然后做不好 |
| 会议没人记录 | 指定一人做纪要，不是"回去凭记忆写" |
