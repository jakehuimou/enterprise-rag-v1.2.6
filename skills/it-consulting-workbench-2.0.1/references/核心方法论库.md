# IT咨询核心方法论库

> 本文档是深度参考, 不需要一次性读完。在相关workflow中使用具体方法论时回查此处。

---

## 1. MECE原则 (Mutually Exclusive, Collectively Exhaustive)

### 核心概念
MECE是结构化思维的基石。任何问题的分解都必须满足:
- **相互独立** (Mutually Exclusive): 各部分之间不重叠
- **完全穷尽** (Collectively Exhaustive): 各部分合起来覆盖全部

### IT咨询中的经典MECE分解

**IT能力五维分解** (最常用):
```
IT能力 = 技术 + 流程 + 组织 + 数据 + 财务
```

**IT投资三分法:**
```
IT总支出 = Run (运维) + Grow (增长) + Transform (转型)
```

**应用系统三分法 (Pace-Layered):**
```
应用组合 = SoR (记录型系统) + SoD (差异化系统) + SoI (创新型系统)
```

**技术栈分层:**
```
技术栈 = 基础设施层 + 平台层 + 应用层 + 渠道/接入层 + 安全层
```

**IT问题诊断五维:**
```
问题根因 ∈ {技术原因, 流程原因, 组织原因, 数据原因, 外部原因}
```

### MECE自检清单
每次分解后问自己:
1. ME检查: "有没有两个分支说的是同一件事?"
2. CE检查: "有没有遗漏任何可能性?"
3. 同级检查: "所有分支是否在同一抽象层级?"

## 2. 假设驱动方法 (Hypothesis-Driven Approach)

### 传统 vs 假设驱动

| | 传统方法 | 假设驱动 |
|------|---------|---------|
| 起点 | 数据 | 假设 |
| 路径 | 收集→分析→发现→结论 | 假设→验证→迭代 |
| 效率 | 分析100%, 80%是无用功 | 只分析关键的20% |
| 典型问题 | 分析瘫痪 | 确认偏误 (需要警惕) |

### 假设驱动的核心流程
1. **Day 1提出假设**: 基于经验和初步信息
2. **设计验证方案**: "如果X为真, 我们应该观察到Y"
3. **快速验证**: 48小时内证伪或证实
4. **迭代精化**: 保留被证实的, 修正被证伪的
5. **在第3-4天形成初步判断**

### 假设的表述标准
- Bad: "系统性能不行"
- Good (可验证): "如果核心交易系统性能是瓶颈, 我们应该观察到P99响应时间>500ms, 且高峰期CPU利用率>85%"

## 3. 金字塔原理 (Pyramid Principle)

### 结构
```
         ┌──────────────┐
         │   核心结论     │  ← 先给答案
         └──────┬───────┘
    ┌───────────┼───────────┐
┌───┴───┐   ┌───┴───┐   ┌───┴───┐
│论据 1  │   │论据 2  │   │论据 3  │  ← 支撑结论的关键论点
└───┬───┘   └───┬───┘   └───┬───┘
 数据/事实    数据/事实    数据/事实    ← 支持论点的证据
```

### 四条铁律
1. 任何层级的论点必须是对下级论点的总结 (Summary)
2. 同级别论点必须遵循MECE
3. 同级别论点必须按逻辑顺序排列 (演绎/时间/结构/程度)
4. 每个论点至少2个支撑, 最多7个 (2-7法则)

### SCQA叙事框架 (用于执行摘要和汇报开场)
- **S**ituation (情境): "我们处在什么环境中?" — 现状, 共识, 不引起争议
- **C**omplication (冲突): "发生了什么变化?" — 问题, 挑战, 机会
- **Q**uestion (问题): "需要回答什么核心问题?"
- **A**nswer (答案): "我的建议是什么?" (直接给出)

## 4. 80/20法则 (Pareto Principle)

### 在咨询中的应用
- **发现问题**: 20%的系统可能造成80%的故障, 聚焦这20%
- **分析问题**: 20%的分析维度可能贡献80%的洞察, 先做这些
- **解决问题**: 20%的举措可能产生80%的收益, 优先排入Wave 1

### 实操: 如何找到20%
1. 列出所有可能的因素/发现/建议
2. 给每个打分 (影响程度 1-5)
3. 只保留4-5分的
4. 问自己: "如果只能做3件事, 哪些是不做会后悔的?"

## 5. Issue Tree vs Hypothesis Tree vs Driver Tree

| 类型 | 结构 | 数据需求 | 使用时机 | 输出 |
|------|------|---------|---------|------|
| Issue Tree | 按逻辑/类别分解 | 无需数据 | 问题定义阶段——"问题可能出在哪里?" | 所有可能的原因 |
| Hypothesis Tree | 按假设分解, 每个分支可验证 | 少量数据 | 探索阶段——"最可能的原因是什么?" | 验证过/推翻过的假设 |
| Driver Tree | 按数学关系分解 | 需要数据 | 量化阶段——"每个因素的影响有多大?" | 量化影响排序 |

### 使用顺序
Issue Tree (宽泛探索) → Hypothesis Tree (聚焦验证) → Driver Tree (量化影响)

## 6. 根因分析 (Root Cause Analysis)

### 5-Why 技术
连续问5次"为什么", 直到找到真正的系统性问题:

```
现象: 新功能上线太慢 (4个月)
Why 1: 因为开发后测试花了3周
Why 2: 因为每次都要做全量回归测试
Why 3: 因为自动化测试覆盖率只有15%
Why 4: 因为团队在过去3年从未被要求写测试
Why 5: 因为绩效考核只衡量"功能上线数量", 不算"质量和技术债务"

表面原因: 测试太慢
根本原因: 绩效考核体系激励短期交付, 惩罚长期质量投入
```

### 鱼骨图 (Ishikawa Diagram)
将问题放在"鱼头", 从4-6个维度分别展开可能原因:
```
                    人            流程
                      \           /
                       \         /
                        \       /
              技术 ———— 问题 ———— 数据
                        /       \
                       /         \
                      /           \
                   系统          外部
```

## 7. 常用战略框架速览

### McKinsey 3 Horizons
| Horizon | 时间 | 焦点 | IT重点 |
|---------|------|------|--------|
| H1 | 0-12月 | 捍卫和拓展现有业务 | 效率提升/成本优化/稳定运营 |
| H2 | 12-36月 | 建立新兴业务 | 新平台建设/数字化能力/数据驱动 |
| H3 | 36月+ | 创造未来选项 | 前沿技术实验/AI创新/生态建设 |

### McKinsey 7S
硬要素: **S**trategy(战略) → **S**tructure(结构) → **S**ystems(系统)
软要素: **S**hared Values(共同价值观) → **S**tyle(风格) → **S**taff(人员) → **S**kills(技能)

### Porter 5 Forces (用于行业竞争分析)
1. 新进入者威胁
2. 供应商议价能力
3. 买方议价能力
4. 替代品威胁
5. 现有竞争者竞争强度

### PESTEL (宏观环境分析)
**P**olitical(政治) → **E**conomic(经济) → **S**ocial(社会) → **T**echnological(技术) → **E**nvironmental(环境) → **L**egal(法律)

### SWOT (内部+外部综合分析)
内部: **S**trengths(优势) + **W**eaknesses(劣势)
外部: **O**pportunities(机会) + **T**hreats(威胁)
→ 交叉分析: SO策略(用优势抓机会) / WT策略(补救劣势防威胁)

## 8. IT专用框架速览

### TOGAF ADM (企业架构开发方法)
10个阶段, 需求管理贯穿始终:
Preliminary → A.Vision → B.Business Architecture → C.IS Architecture (Data+App) → D.Technology Architecture → E.Opportunities & Solutions → F.Migration Planning → G.Implementation Governance → H.Architecture Change Management

### Well-Architected Framework (云架构最佳实践)
五大支柱: 卓越运营 / 安全 / 可靠性 / 性能效率 / 成本优化

### ITIL 4 (IT服务管理)
服务价值链: 计划 → 改进 → 参与 → 设计与转换 → 获取/构建 → 交付与支持

### 6R Cloud Migration
Retire → Retain → Rehost → Replatform → Refactor → Reimagine
(从最低到最高颠覆性排列)

### NIST CSF 2.0 (网络安全框架)
六大功能: GOVERN(治理) → IDENTIFY(识别) → PROTECT(保护) → DETECT(检测) → RESPOND(响应) → RECOVER(恢复)

### FinOps Maturity
三阶段: Inform(信息透明) → Optimize(优化) → Operate(持续运营)

## 9. 框架选择决策树

```
你面对什么问题?
│
├── 问题不清晰, 需要定义问题本身 → Issue Tree + MECE
├── 问题清晰, 需要找根因 → 5-Why + 鱼骨图
├── 需要制定战略 → McKinsey 3 Horizons + SWOT + PESTEL
├── 需要组织设计 → McKinsey 7S
├── 需要评估行业位置 → Porter 5 Forces
├── 需要做投资决策 → NPV/IRR + 决策树 + 敏感性分析
├── 需要管理变革 → Kotter 8-Step + ADKAR
├── 需要设计IT架构 → TOGAF ADM
├── 需要上云 → 6R + Well-Architected
├── 需要做安全评估 → NIST CSF 2.0
├── 需要做AI规划 → AIM² + RICE+ + 5D Framework
└── 需要优化成本 → FinOps + TCO + TBM
```

## 10. McKinsey AI价值创造三波浪潮

### 三波概览
| 波次 | 时间 | 核心特征 | 价值创造 |
|------|------|---------|---------|
| 第一波: 技术赋能 | 2023-2026 | LLM/Copilot/自动化嵌入现有流程 | 效率提升15-40%，成本降低 |
| 第二波: 流程重塑 | 2025-2028 | AI Agent/多模态/领域模型重新设计流程 | 产品/服务AI化，新商业模式 |
| 第三波: 模式创新 | 2027-2030+ | AGI雏形/人机协作/制度变革 | 行业边界重塑，新市场诞生 |

> 注：以上时间窗与 GenAI 数据口径以 SKILL.md 主文「McKinsey AI 价值创造三波浪潮」为**单一事实源**（已于 2026-07 对齐；旧口径 2022-2024/2024-2027 为历史版本，不再使用）。

### GenAI落地鸿沟
- **全漏斗**：88%企业已使用AI → 46%规模化应用GenAI → 仅9%实现显著商业价值（与 SKILL.md 对齐，McKinsey 2025-2026，截至2025全年）
- 三大根因: 数据就绪度不足(62%)、人才短缺(55%)、治理缺失(48%)

### AI高绩效者六大画像
| 维度 | 高绩效者 | 落后者 |

| 数据 | 企业数据平台+数据产品思维 | 数据孤岛，手工ETL |

## 13. 零信任安全架构（NIST SP 800-207）

三大核心原则: ①永不信任始终验证 ②最小权限(JIT+JEA) ③假设已入侵

三大技术路径: SASE(云原生安全+SD-WAN) / ZTNA(应用级隧道替代VPN) / 微隔离(工作负载间精细化)

2026趋势: AI自适应策略、ITDR成为独立品类、OT/IoT零信任框架成熟
